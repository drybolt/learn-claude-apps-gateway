Self-guide — Claude Apps Gateway on AWS

us-east-1 · 단일 AZ · Cognito IdP · Client VPN · 개발자 랩탑에서 직접 로그인 흐름을 확인하는 최소 구성.

이 가이드는 Claude Apps Gateway가 실제로 동작하는지 가장 빠르게 확인하는 것을 목표로 한다. 운영용 정석 구성(RDS·ALB·다중 AZ) 대신, 로그인과 추론이 끝까지 되는 것만 보기 위해 최소한으로 줄였다. 클라이언트는 개발자 랩탑 하나이며, Client VPN으로 VPC에 진입해 게이트웨이에 접속한다. 정석 구성으로 넘어가는 지점은 각 단계에서 따로 표시한다.

이 구성은 테스트 전용이다. PostgreSQL을 관리형 RDS 대신 별도 Fargate 컨테이너로 두고, TLS는 게이트웨이 자체 listener(listen.tls)로 자체 서명 인증서를 종단한다. 이 두 선택은 각각 RDS(2 AZ 필수)와 ALB(2 AZ 필수)의 이중화 요건을 피하기 위한 것이다. 공인 인증서나 관리형 DB의 백업·가용성이 필요해지면 정석 구성으로 전환해야 한다.

목표 구성

[개발자 랩탑: Claude Code CLI + 브라우저]
   |  ① AWS Client VPN 터널(mutual TLS)로 VPC 진입
   v
   VPC (us-east-1, 단일 AZ)
   +- Public Subnet:  NAT Gateway (게이트웨이의 아웃바운드용)
   +- Private Subnet: Client VPN ENI --(② 사설 IP)--> claude gateway
                      ECS Task(gateway):  claude gateway (listen.tls로 HTTPS 종단)
                      ECS Task(postgres): postgres:16   <- RDS 대체, Cloud Map DNS
                      Amazon Bedrock (업스트림)

[Cognito] <-- 브라우저 SSO(공개 인터넷) · 게이트웨이 토큰 검증(NAT 경유)

전제 조건 (미리 갖춰야 할 것)

  • AWS 계정과 us-east-1 사용 권한 (VPC·ECS·IAM·Cognito·Bedrock·Client VPN·Route53·Cloud Map 생성 권한)
  • 개발자 랩탑에 Claude Code v2.1.195 이상 설치, 게이트웨이 컨테이너의 바이너리도 동일 버전 이상
  • 랩탑에 AWS VPN Client 앱과 인증서 생성용 easy-rsa(OpenVPN) — mutual TLS 인증서는 단계 3(Client VPN 설정)에서 직접 만든다
단계 사이에 의존이 있어 순서가 중요하다. Cognito App Client의 콜백 URL에는 게이트웨이 hostname이 필요하고(단계 1), 그 hostname의 실제 IP 매핑은 게이트웨이 배포 후에야 정해진다(단계 5). 이 순환을 풀기 위해 단계 0에서 hostname을 "이름만" 먼저 확정한다. 이름은 IP가 없어도 정할 수 있으므로, 이후 Cognito·Route53·gateway.yaml이 모두 그 이름을 참조하고, 이름→IP 매핑만 나중에 채운다.

단계 0 · 사전 준비 (다른 단계가 의존하는 값 확정)

  1. 게이트웨이 hostname을 이름으로 확정한다 (예: claude-gw.internal.example.com). 아직 리소스를 만들지 않고 이름만 정한다 — 이후 Cognito 콜백(단계 1), Route53 A 레코드(단계 2·5), gateway.yaml의 public_url(단계 4), managed-settings.json(단계 6)이 전부 이 이름을 쓴다. 이 이름은 실제로 소유한 도메인일 필요가 없다 — 단계 2의 Route53 private hosted zone은 VPC 안에서만 유효하고 인터넷 DNS와 분리되므로, internal.example.com 같은 임의의 이름을 도메인 구매 없이 쓸 수 있다.
  2. CIDR 대역을 정한다. 아래 값을 기본 제안으로 쓴다. 이 값에서 Route53 Resolver 주소(VPC CIDR의 +2)와 Client VPN 클라이언트 대역이 파생되므로 먼저 확정한다.
    항목CIDR비고
    VPC10.0.0.0/16Route53 Resolver = 10.0.0.2
    ├ Public Subnet10.0.0.0/24NAT Gateway 배치
    └ Private Subnet10.0.1.0/24gateway·postgres Task, Client VPN 연결
    Client VPN 클라이언트172.16.0.0/22VPC와 겹치지 않는 대역
  3. Bedrock 모델 액세스를 활성화한다 (us-east-1, Opus·Sonnet·Haiku). 승인에 시간이 걸릴 수 있어 가장 먼저 신청해 둔다.
CIDR 두 개는 서로도, 랩탑의 로컬망과도 겹치면 안 된다. Client VPN 클라이언트 대역(172.16.0.0/22)을 VPC(10.0.0.0/16)와 다른 대역으로 둬야, 랩탑이 VPN에 붙었을 때 주소가 충돌하지 않는다. 클라이언트 CIDR은 AWS 제약상 /22 이상이어야 해서 /24가 아니라 /22를 썼다. 또한 랩탑이 접속하는 로컬망이나 회사 VPN이 이미 10.0.0.0/16·172.16.0.0/22를 쓰면 라우팅이 충돌하므로, 테스트 전 랩탑에서 ifconfig(macOS·Linux)나 ipconfig(Windows)로 현재 IP 대역을 확인한다. 겹치면 VPC를 10.20.0.0/16 같은 덜 흔한 대역으로 바꾼다.

단계 1 · Cognito (OIDC IdP) 준비

선행: 단계 0의 게이트웨이 hostname. Claude Apps Gateway는 로그인 전체를 IdP에 위임하므로, IdP 없이는 어떤 테스트도 시작할 수 없다(SAML·LDAP 미지원, OIDC 전용).

상세 절차는 Cognito 설정 문서에서 다룬다. 최신 콘솔은 애플리케이션 중심 흐름이라 애플리케이션 정보만 입력하면 User Pool과 App Client가 함께 자동 생성된다(풀 이름을 먼저 입력하는 칸은 없다). 요지만 정리하면:

  • Application type = Traditional web application (client secret을 쓰는 confidential 클라이언트 → 게이트웨이 설정과 맞음)
  • 사인인 옵션 = Email, 필수 속성 = email (생성 후 변경 불가)
  • 콜백 URL = https://<gateway-hostname>/oauth/callback
  • 생성 후: 이메일 자동 검증 활성화, MFA 끄기, Hosted UI 도메인 생성, 테스트 사용자를 email_verified: true로 생성

다음 세 값을 메모해 단계 4의 gateway.yaml oidc 블록에 넣는다: issuer(https://cognito-idp.us-east-1.amazonaws.com/<pool-id>), client_id, client_secret.

Cognito는 공개 엔드포인트라 브라우저 도달 문제가 없다. 사설 IP resolution 제약은 게이트웨이 자신에만 적용되고 IdP에는 적용되지 않는다. Cognito 로그인 페이지는 공개 인터넷에서 열리므로, 랩탑 브라우저가 Cognito에 닿는 것은 문제가 아니다. 대신 게이트웨이(사설 IP)에 닿는 경로는 단계 2·3에서 Client VPN으로 마련한다.

단계 2 · 네트워크 (단일 AZ)

선행: 단계 0의 VPC CIDR·hostname.

  1. 단계 0의 표대로 VPC(10.0.0.0/16) + Public Subnet(10.0.0.0/24) + Private Subnet(10.0.1.0/24)을 만든다
  2. NAT Gateway를 Public Subnet에 배치 — 게이트웨이가 Cognito·Bedrock·ECR로 나가는 아웃바운드 경로. Cognito는 VPC 엔드포인트를 제공하지 않으므로 NAT가 사실상 필수다. (이 구성에서 Public Subnet은 NAT 전용이다 — 클라이언트 EC2는 두지 않는다.)
  3. VPC 속성 enableDnsHostnames와 enableDnsSupport를 둘 다 true로 설정한다 — 이게 꺼져 있으면 다음의 private hosted zone이 동작하지 않는다.
  4. Route53 private hosted zone을 만들어(도메인 이름 = hostname의 부모 도메인 internal.example.com, Type = Private hosted zone) 이 VPC에 연결한다. 게이트웨이 hostname의 A 레코드(이름 = claude-gw)는 gateway Task(ECS)의 사설 IP가 나오는 단계 5에서 채운다(지금은 zone만 준비). VPN으로 들어온 랩탑은 이후 이 이름을 사설 IP로 resolve하게 된다. VPC DNS 속성 확인부터 zone 생성·A 레코드까지의 전체 절차는 Route53 Private Zone 설정 문서에서 다룬다.
NAT가 없으면 로그인이 실패한다. 게이트웨이는 Cognito에 토큰을 검증하러 나가야 하는데, Cognito는 VPC 엔드포인트가 없어 이 아웃바운드가 NAT를 거친다. NAT가 없으면 이 경로가 막혀 로그인이 완료되지 않는다.
zone 이름은 hostname 전체가 아니라 부모 도메인이다 (헷갈리기 쉬운 지점). zone 도메인 이름에는 게이트웨이 hostname 전체(claude-gw.internal.example.com)가 아니라 그 부모 도메인(internal.example.com)을 입력한다. hosted zone은 자기 도메인 이름과 그 하위(subdomain) 레코드를 담는 그릇이므로, 부모 도메인으로 zone을 만들면 그 안에 이름이 claude-gw인 레코드를 두어 완성 이름 claude-gw.internal.example.com을 만든다("레코드 이름 + zone 이름"이 합쳐진다). 이렇게 하면 db·api 같은 형제 이름을 같은 zone에 나란히 추가할 수 있어, 게이트웨이 외에 이름 있는 리소스를 더 두거나 운영 환경으로 확장할 때 자연스럽다. 자세한 절차는 Route53 Private Zone 설정 문서에 있다.

단계 3 · AWS Client VPN (랩탑 → VPC 진입)

선행: 단계 2의 VPC·Private Subnet. 랩탑은 VPC 밖에 있어, Private Subnet의 게이트웨이에 인터넷에서 직접 닿을 수 없다(게이트웨이는 사설 IP로만 접근을 허용한다). Client VPN으로 랩탑을 VPC 사설망에 넣어, 랩탑의 Claude Code CLI와 브라우저가 모두 게이트웨이에 도달하게 한다.

인증서 생성(easy-rsa)부터 ACM 업로드, 엔드포인트 구성, 랩탑 접속까지의 전체 절차는 Client VPN 설정 문서에서 다룬다. 요점만 정리하면:

  • mutual TLS 인증 — easy-rsa로 CA·서버·클라이언트 인증서를 만들고, 서버 인증서를 us-east-1 ACM에 업로드한다.
  • 엔드포인트의 클라이언트 CIDR = 172.16.0.0/22(단계 0), Private Subnet에 연결, VPC CIDR 허용 규칙 추가.
  • DNS 서버 = VPC Route53 Resolver(10.0.0.2) — 이래야 랩탑이 게이트웨이 hostname을 사설 IP로 resolve한다(가장 자주 누락되는 항목).

단계 4 · gateway.yaml

선행: 단계 0의 hostname, 단계 1의 Cognito 값. 이 설정 파일을 먼저 작성해야 다음 단계에서 gateway 이미지를 빌드·배포할 수 있다. postgres를 가리키는 Cloud Map 이름(postgres.claude-gw.local)은 우리가 정하는 규칙이므로, 배포 전이라도 미리 확정해 여기에 쓴다.

listen:
  host: 0.0.0.0
  port: 8080
  public_url: https://<gateway-hostname>      # 랩탑 CLI·브라우저가 접근하는 이름
  tls:                                         # 게이트웨이가 직접 HTTPS 종단
    cert_file: /etc/claude/tls/cert.pem
    key_file: /etc/claude/tls/key.pem

oidc:
  issuer: https://cognito-idp.us-east-1.amazonaws.com/<pool-id>
  client_id: <cognito-app-client-id>
  client_secret: ${OIDC_CLIENT_SECRET}
  allowed_email_domains: [<your-domain>]

session:
  jwt_secret: ${GATEWAY_JWT_SECRET}
  ttl_hours: 1

store:
  # 별도 postgres Task를 Cloud Map 이름으로 가리킨다 (localhost 아님)
  postgres_url: ${GATEWAY_POSTGRES_URL}        # postgres://user:pass@postgres.claude-gw.local:5432/gateway

upstreams:
  - provider: bedrock
    region: us-east-1
    auth: {}                                   # 비우면 Task Role 사용
    auto_include_builtin_models: true

이 gateway.yaml과 TLS 인증서를 gateway 컨테이너 이미지에 포함하는 방법은 이미지 준비에서 다룬다.

단계 5 · Fargate — gateway·postgres 별도 Task

선행: 단계 4의 gateway.yaml, 이미지 준비에서 만든 두 컨테이너 이미지, 단계 1의 Cognito 값, 단계 2의 서브넷. gateway와 postgres를 별도의 ECS Task로 분리한다.

  1. postgres Task/Service — postgres:16 이미지를 ECS Service로 띄우고 Private Subnet에 배치한다. 서비스 생성 화면의 Service Discovery 설정에서 네임스페이스 이름(claude-gw.local)과 서비스 이름(postgres)을 입력하면, ECS가 Cloud Map private DNS namespace를 자동으로 생성하고 이 Task를 postgres.claude-gw.local로 등록한다(단계 4의 postgres_url과 일치). 즉 Cloud Map을 별도로 먼저 만들 필요가 없다.
  2. gateway Task/Service — 이미지 준비에서 ECR에 올린 gateway 이미지로 ECS Service를 띄운다. 위 postgres와 같은 네임스페이스(claude-gw.local)를 지정해, 게이트웨이가 postgres.claude-gw.local로 DB를 찾게 한다. (이 이미지에는 단계 4의 gateway.yaml과 TLS 인증서가 이미 포함돼 있어 listen.tls로 HTTPS를 직접 종단한다.)
  3. Task Role(gateway)에 bedrock:InvokeModel 등 Bedrock 호출 권한 부여
  4. 보안 그룹 — postgres SG는 gateway SG로부터의 5432를 허용하고, gateway SG는 Client VPN 클라이언트 CIDR로부터의 443을 허용한다.
  5. 비밀값 주입: OIDC_CLIENT_SECRET·GATEWAY_JWT_SECRET·GATEWAY_POSTGRES_URL·admin 키 (테스트면 Task Definition 환경변수 직접 주입도 가능)
  6. gateway Task의 사설 IP가 정해지면, 단계 2에서 만든 private hosted zone에 A 레코드를 채운다(hostname → 이 사설 IP). 이것으로 단계 0에서 이름만 정해 둔 hostname이 실제 IP와 연결된다.
별도 Task라 gateway 재배포에도 상태가 유지된다. 사이드카(같은 Task) 방식과 달리, gateway만 재시작해도 postgres Task는 살아 있어 로그인·세션 상태가 보존된다. 다만 postgres 컨테이너 자체가 교체되면(재배포·장애) 상태는 사라지므로, 영속 저장이 필요하면 EFS 볼륨을 붙이거나 RDS로 전환한다.

단계 6 · 클라이언트(랩탑) 설정

선행: 단계 0의 hostname.

  1. 랩탑에 Claude Code v2.1.195+ 설치
  2. managed-settings.json에 게이트웨이 강제 로그인 설정을 작성한다. 경로는 랩탑 OS에 따라 다르다:
    • macOS: /Library/Application Support/ClaudeCode/managed-settings.json
    • Linux/WSL: /etc/claude-code/managed-settings.json
    • Windows: C:\Program Files\ClaudeCode\managed-settings.json
    {
  "forceLoginMethod": "gateway",
  "forceLoginGatewayUrl": "https://<gateway-hostname>"
}

단계 7 · 로그인·추론 테스트 (성공 판정)

  1. 랩탑에서 AWS VPN Client로 Client VPN에 접속한다(VPC 진입).
  2. nslookup <gateway-hostname>으로 사설 IP가 나오는지 먼저 확인한다(DNS 검증).
  3. 랩탑 터미널에서 claude 실행 후 /login
  4. CLI가 사용자 코드와 확인 URL을 표시한다
  5. 같은 랩탑의 브라우저에서 그 URL을 열고, 사용자 코드를 입력한다
  6. Cognito 로그인 화면에서 테스트 사용자로 로그인·승인한다
  7. CLI의 polling이 세션 토큰을 받아 대기를 끝낸다
  8. 모델을 호출해 응답이 오면 성공이다

이 흐름의 내부 동작(디바이스 코드·polling·리다이렉트)이 궁금하면 디바이스 인증 플로우 자세히를 참고한다. CLI와 브라우저가 같은 랩탑에 있으므로, 디바이스 플로우가 "서로 다른 기기"일 필요가 없는 가장 단순한 형태로 동작한다.

막히면 여기부터 확인

  • hostname resolve 실패 — nslookup이 사설 IP를 안 주면, Client VPN의 DNS가 VPC Route53 Resolver로 설정됐는지, private hosted zone에 A 레코드가 있는지 확인한다.
  • VPN 연결됐는데 게이트웨이 접근 불가 — Client VPN authorization rule에 VPC CIDR 허용이 있는지, gateway SG가 클라이언트 CIDR의 443을 허용하는지 확인한다.
  • 게이트웨이가 DB 연결 실패 — GATEWAY_POSTGRES_URL의 Cloud Map 이름이 맞는지, postgres SG가 gateway SG의 5432를 허용하는지 확인한다.
  • 사설 IP 거부 — 게이트웨이 hostname이 공개 IP로 resolve되면 /login이 거부된다. 사설 IP로 풀리는지 확인한다.
  • 로그인 콜백 실패 — public_url과 Cognito에 등록한 redirect_uri가 정확히 일치하는지 확인한다.
  • 토큰 검증 실패 — gateway Task가 NAT를 통해 Cognito로 나가는지, 테스트 사용자의 email_verified가 true인지 확인한다.
  • 모델 호출 실패 — Bedrock 모델 액세스가 활성화됐는지, Task Role에 bedrock:InvokeModel이 있는지 확인한다.

정석 구성으로 전환하는 지점

  • 관리형 DB·백업·가용성 필요 → 별도 postgres Task를 RDS PostgreSQL(2 AZ)로 교체
  • 공인 인증서·확장성 필요 → 게이트웨이 자체 TLS를 ALB(2 AZ, ACM 인증서) 종단으로 교체
  • 상시·전사 접속 필요 → Client VPN을 Direct Connect나 Site-to-Site VPN 기반의 상시 사설 연결로 교체(블로그가 제시하는 운영 구성)
  • 그룹별 모델·사용량 제어 → gateway.yaml에 managed·admin 블록 추가 (gateway.yaml 설정 구조의 선택 블록 참고)
  • 사용량 모니터링 → telemetry 블록으로 CloudWatch 연동

이미지 준비 — gateway · postgres

실습 가이드 단계 5에서 배포할 두 컨테이너 이미지를 준비한다.

실습 가이드의 단계 5는 gateway와 postgres를 별도 ECS Task로 띄운다. 두 이미지는 성격이 전혀 달라, 하나는 직접 빌드해야 하고 하나는 공개 이미지를 그대로 쓴다. 이 문서는 그 준비 과정만 따로 다룬다.

사전 준비 환경 (macOS 기준)

아래 준비물은 모두 gateway 이미지 빌드에 필요한 것이다(postgres는 공개 이미지라 별도 준비물이 없다).

  • 네이티브 claude 바이너리 (1단계) — v2.1.195 이상. Claude Code 설치 스크립트의 native(standalone) 설치로 최신 버전을 받는다. 
    curl -fsSL https://claude.ai/install.sh | bash
    게이트웨이 서버 모드는 native 바이너리에서만 동작한다(npm/Node.js 설치본으로는 뜨지 않는다 — 공식 문서). 또한 이미지가 Linux 베이스이므로 macOS용이 아니라 배포 대상 아키텍처의 Linux용 바이너리여야 한다(아래 callout 참고).
  • OpenSSL (2단계) — macOS 기본 openssl은 LibreSSL이며, 문서의 -addext "subjectAltName=…" 옵션이 구버전 LibreSSL에서 동작하지 않을 수 있다. openssl version으로 확인하고, LibreSSL이면 brew install openssl로 정식 OpenSSL(3.x)을 설치해 쓴다.
  • Docker (3·4단계) — Docker Desktop 또는 colima 등 대체 런타임. 이미지 빌드·push에 쓴다.
  • AWS CLI (4단계) — ECR 리포지토리 생성·로그인·push에 쓴다. brew install awscli 후 aws sts get-caller-identity로 us-east-1 접근 인증을 확인한다.
아키텍처를 일치시켜야 한다 — Apple Silicon에서 특히 주의한다. Fargate Task는 cpuArchitecture를 지정하지 않으면 기본이 X86_64다(공식 문서). 반면 Apple Silicon(M1~) 랩탑에서 docker build는 기본으로 arm64 이미지를 만든다. 이 둘이 어긋나면 Task 실행 시 exec format error로 컨테이너가 뜨지 않는다. claude 바이너리 · 빌드한 이미지 · Fargate Task 세 가지의 아키텍처를 모두 일치시켜야 한다.
  • x86_64로 맞추는 경우(기본): Linux x86_64 claude 바이너리를 받고, docker build --platform linux/amd64 …로 빌드한다. Task는 기본값 그대로 둔다.
  • arm64로 맞추는 경우: Linux arm64 바이너리 + --platform linux/arm64로 빌드하고, Task Definition의 cpuArchitecture를 ARM64로 지정한다.

gateway 이미지 — 직접 빌드

Anthropic은 게이트웨이용 컨테이너 이미지를 공개 배포하지 않는다. 게이트웨이 기능은 claude 바이너리에 내장돼 있으므로, 그 네이티브 바이너리를 담은 이미지를 직접 만들어야 한다.

아래 1~3단계는 하나의 빌드 컨텍스트 디렉터리를 채우는 과정이다. Dockerfile의 COPY는 이 디렉터리를 기준으로 한 상대 경로만 참조하므로(4단계의 docker build … .에서 .이 이 디렉터리를 가리킨다), 모든 명령을 이 디렉터리 안에서 실행하고 파일도 전부 여기에 둔다. 

gateway-build/                # 빌드 컨텍스트 (임의 이름, 여기서 모든 명령 실행)
├── claude                    # 1단계: 네이티브 claude 바이너리
├── tls/                      # 2단계: 자체 서명 인증서 (mkdir + openssl)
│   ├── cert.pem
│   └── key.pem
├── gateway.yaml              # 단계 4에서 작성한 설정
└── Dockerfile                # 3단계

1. 네이티브 claude 바이너리 확보

v2.1.195 이상의 네이티브 바이너리가 필요하다. 게이트웨이 서버 모드(claude gateway)는 네이티브 바이너리에서만 동작하며, npm/Node.js 설치본으로는 서버가 뜨지 않는다. 빌드 컨텍스트(Dockerfile과 같은 디렉터리)에 이 바이너리를 claude라는 이름으로 둔다.

2. 자체 서명 TLS 인증서 생성

게이트웨이 hostname(단계 0에서 정한 이름)에 대한 자체 서명 인증서를 만들어 빌드 컨텍스트의 tls/에 둔다. 다음 Dockerfile이 이 tls/cert.pem·tls/key.pem을 COPY하므로, 빌드 전에 먼저 만들어 둔다. 

mkdir -p tls
openssl req -x509 -newkey rsa:2048 -nodes -days 365 \
  -keyout tls/key.pem -out tls/cert.pem \
  -subj "/CN=<gateway-hostname>" \
  -addext "subjectAltName=DNS:<gateway-hostname>"
<gateway-hostname>은 반드시 실제 값으로 치환한다. 이 문자열을 그대로 실행하면 인증서의 SAN(subjectAltName)에 <gateway-hostname>이라는 리터럴 문자열이 그대로 박힌다. 클라이언트가 실제 hostname(예: claude-gw.internal.example.com)으로 접속하면 Hostname/IP does not match certificate's altnames 에러로 실패한다. -subj와 -addext 두 곳 모두 실제 hostname으로 바꿔야 한다.

자체 서명이라 클라이언트가 신뢰하지 않을 수 있다. 랩탑에서는 인증서 전체를 신뢰 저장소에 추가하는 대신, Claude Code의 ~/.claude/settings.json에 env.NODE_EXTRA_CA_CERTS로 tls/cert.pem(공개 인증서, key.pem은 필요 없음) 경로를 지정하는 방법이 더 간단하다 — 자세한 내용은 실습 가이드 단계 6에 있다. (공인 인증서가 필요하면 실습 가이드의 "정석 구성으로 전환" — ALB + ACM으로 넘어간다.)

3. Dockerfile 작성

AWS 블로그 예시를 따른다. 경량 베이스에 바이너리를 복사하고, gateway.yaml과 TLS 인증서를 이미지에 함께 굽는다(테스트 방식 — 아래 callout 참고). ENTRYPOINT는 게이트웨이 서버로 지정한다. 

FROM debian:12-slim                          # glibc 기반 경량 베이스
RUN useradd -m -u 10001 gateway || true
COPY claude /usr/local/bin/claude            # 네이티브 claude 바이너리 복사 (1단계)
RUN chmod +x /usr/local/bin/claude

# --- 테스트 방식: 설정·인증서를 이미지에 굽는다 ---
COPY gateway.yaml /etc/claude/gateway.yaml   # 단계 4에서 작성한 설정
COPY tls/cert.pem /etc/claude/tls/cert.pem   # 자체 서명 인증서 (2단계)
COPY tls/key.pem  /etc/claude/tls/key.pem

ENV CLAUDE_CONFIG_DIR=/tmp/.claude
ENV CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1   # Anthropic으로의 비필수 트래픽 차단
EXPOSE 443
ENTRYPOINT ["claude", "gateway", "--config", "/etc/claude/gateway.yaml"]
EXPOSE는 gateway.yaml의 listen.port와 일치해야 한다. 이 구성은 ALB 없이 게이트웨이가 직접 443을 종단하므로(실습 가이드 단계 4), listen.port: 443과 맞춰 EXPOSE 443을 쓴다. 8080으로 두면 클라이언트가 기본 포트(443)로 접속을 시도할 때 ECONNREFUSED로 거부된다. Dockerfile에 USER 지정이 없어 컨테이너가 root로 실행되므로 443 같은 privileged port를 바인딩하는 데 권한 문제는 없다.
이 테스트는 설정·인증서를 이미지에 굽는다 — 편의를 위한 선택이다. gateway.yaml과 TLS 인증서를 COPY로 이미지에 포함하면 별도 볼륨·시크릿 마운트가 필요 없어 가장 단순하다. 단, 비밀값(OIDC_CLIENT_SECRET 등)은 이미지에 굽지 않는다 — gateway.yaml이 ${ENV_VAR}로 참조하고, 실제 값은 ECS Task Definition의 환경변수(또는 Secrets Manager)로 런타임에 주입한다. 자체 서명 인증서와 설정이 이미지에 남는 것은 테스트라 용인하지만, 운영에서는 인증서를 Secrets Manager에서 마운트하고 설정도 이미지 밖에서 주입하는 방식으로 전환한다.

4. ECR에 push

Fargate가 pull할 수 있도록 ECR 리포지토리에 올린다. 

aws ecr create-repository --repository-name claude-gateway --region us-east-1

aws ecr get-login-password --region us-east-1 \
  | docker login --username AWS --password-stdin <account-id>.dkr.ecr.us-east-1.amazonaws.com

docker build -t claude-gateway:test .
docker tag  claude-gateway:test <account-id>.dkr.ecr.us-east-1.amazonaws.com/claude-gateway:test
docker push <account-id>.dkr.ecr.us-east-1.amazonaws.com/claude-gateway:test

이 이미지 URI를 단계 5의 gateway Task Definition에 지정한다.

Task Definition에는 태그로 지정한다 — 다이제스트로 고정하지 않는다. ...claude-gateway:test처럼 태그로 지정해야, 이후 같은 태그로 재빌드·push한 뒤 aws ecs update-service --force-new-deployment로 최신 이미지를 실제로 반영할 수 있다. 이미지 필드가 ...claude-gateway@sha256:... 같은 다이제스트로 고정돼 있으면, 태그가 새 다이제스트로 옮겨가도 ECS는 그 옛 다이제스트만 계속 pull한다.

postgres 이미지 — 공개 이미지 그대로

직접 만들 것이 없다. Docker Hub 공식 postgres:16을 ECS Task Definition의 이미지로 지정하고, 초기화 값은 환경변수로 준다.

  • POSTGRES_USER·POSTGRES_PASSWORD·POSTGRES_DB — 이 값들이 gateway의 GATEWAY_POSTGRES_URL(postgres://user:pass@postgres.claude-gw.local:5432/db)과 정확히 일치해야 한다.
  • PostgreSQL 14 이상이면 된다(게이트웨이 요건). postgres:16은 이를 충족한다.
Docker Hub rate limit에 걸릴 수 있다. Fargate가 Docker Hub에서 직접 pull하면 익명 pull rate limit에 걸릴 수 있다. 안정성을 원하면 postgres:16을 ECR로 한 번 미러링(pull → tag → push)해 두고 그 ECR URI를 쓴다. 테스트에서 한두 번 띄우는 정도면 Docker Hub 직접 pull로도 대개 문제없다.

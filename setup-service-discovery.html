ECS Service Discovery (AWS Cloud Map) — Task IP가 바뀌어도 이름이 따라가는 원리

Fargate Task는 고정 IP를 가질 수 없어, 재배포되면 사설 IP가 바뀐다. Service Discovery는 이 바뀌는 IP를 ECS가 자동으로 DNS에 반영해, hostname이 항상 현재 Task를 가리키게 한다.

Route53 Private Zone 설정에서는 A 레코드에 gateway Task의 사설 IP를 손으로 채웠다. 하지만 Fargate Task에는 고정 IP·Elastic IP를 붙일 수 없어(AWS 공식 문서), Task가 재생성되면 ENI가 새로 만들어지며 IP가 바뀐다. 그러면 손으로 채운 A 레코드는 낡은 IP를 가리키게 되어, 재배포 때마다 레코드를 다시 채워야 한다. ECS Service Discovery는 이 갱신을 ECS가 대신 하도록 만드는 방법이다.

"IP를 고정"하는 게 아니라 "이름이 현재 IP를 따라가게" 한다. Service Discovery는 Task의 IP를 고정시키지 않는다. 대신 ECS가 Task의 생성·소멸을 AWS Cloud Map에 계속 알려주고, Cloud Map이 그에 맞춰 Route53 private hosted zone의 DNS 레코드를 갱신한다. 클라이언트는 바뀌지 않는 이름으로 접근하고, 그 이름이 항상 현재 살아 있는 Task의 사설 IP로 resolve된다.

1 · 관계 — ECS Service Discovery · Cloud Map · Route53

"ECS Service Discovery"·"AWS Cloud Map"·"Route53"은 같은 층위의 세 대안이 아니라, 기능 → 서비스 → DNS 백엔드로 이어지는 세 층위의 관계다(공식 문서 "What Is AWS Cloud Map", "AWS Cloud Map service DNS configuration"). 아래 다이어그램이 그 관계다.

역할 분담 — 감지·반영은 ECS 컨트롤 플레인, 레코드 생성은 Cloud Map·Route53. Service Discovery는 컨트롤 플레인 안의 별도 컴포넌트가 아니라, ECS 컨트롤 플레인이 하는 동작 자체를 가리키는 이름이다. Task의 생성·소멸을 감지하고 그 상태를 Cloud Map API로 알리는 것까지가 ECS 컨트롤 플레인의 역할이고, 그 상태를 실제 registry 항목(instance)으로 만들고 — namespace 타입이 Private/Public DNS라면 — Route53 레코드까지 갱신하는 것은 Cloud Map의 역할이다.
Route53에 직접 반영하지 않고 Cloud Map을 거치는 이유.
  • Route53만으로 담을 수 없는 정보를 옮긴다. instance에는 IP 외에 AVAILABILITY_ZONE·ECS_SERVICE_NAME·ECS_CLUSTER_NAME 같은 커스텀 속성이 붙는데, 이는 DiscoverInstances API 조회로만 꺼낼 수 있고 DNS A 레코드에는 담을 수 없다.
  • DNS는 namespace 타입에 따라 선택적이다. Cloud Map은 HTTP(API 전용)·Private DNS·Public DNS 세 종류의 namespace를 지원한다. ECS가 Cloud Map API를 대상으로 통합해 두면 namespace 타입과 무관하게 같은 방식(register/deregister-instance)으로 동작한다.
  • 헬스 체크·zone 생명주기 관리를 대신 해준다. Cloud Map이 Route53 헬스 체크(또는 서드파티 헬스 체커)를 오케스트레이션해 unhealthy 엔드포인트를 조회 결과에서 자동으로 제거하고, private hosted zone의 생성·연결도 namespace 생성 시점에 자동으로 처리한다.
  • ECS 전용이 아닌 범용 레지스트리다. Cloud Map은 ECS/EKS Task뿐 아니라 EC2·S3·DynamoDB·SQS 같은 리소스도 등록할 수 있는 공통 서비스 디스커버리 레이어다. ECS는 이 공통 레이어를 재사용한다.

2 · 구성 요소 — namespace · service · instance

Service Discovery는 AWS Cloud Map API로 동작하며, 세 계층으로 이루어진다(공식 문서 "Service Discovery concepts"). 아래 다이어그램이 그 포함 관계다.

  • Namespace — 같은 도메인 이름을 공유하는 service들의 논리적 묶음(예: internal.example.com). aws servicediscovery create-private-dns-namespace로 만든다. Route53 zone이 자동 생성되는 원리는 위 다이어그램 참고.
  • Service — namespace 안에 있고, 서비스 이름과 DNS 설정(레코드 타입·TTL)으로 이루어진다. Service 자체가 곧 registry다 — 별도의 리소스가 아니라, Service가 instance를 등록받는 역할을 할 때 부르는 이름이다. 4절 CLI에서 ECS create-service에 넘기는 --service-registries "registryArn=..."이 가리키는 대상도 이 Service의 ARN이다. Service를 DNS나 Cloud Map API로 조회하면 등록된 instance들의 엔드포인트를 돌려준다.
  • Instance — Service(registry)에 등록된 각 항목으로, service discovery를 켠 Task 하나에 대응한다. 각 instance에는 메타데이터가 붙는데, A 레코드용 IPv4 주소는 AWS_INSTANCE_IPV4 속성에 담긴다. Task가 여럿이면 instance도 여럿이고, 조회 시 그 IP들의 집합이 반환된다.
  • ECS 헬스 체크 — ECS가 컨테이너 수준 헬스 체크를 주기적으로 수행한다. 헬스 체크를 통과하지 못한 엔드포인트는 DNS 라우팅에서 제외되고 unhealthy로 표시된다.

Cloud Map의 세 계층은 DNS의 계층 구조와 그대로 대응한다. 다만 DNS는 원래 정적인 개념(누군가 손으로 채우는 레코드)인데, Cloud Map은 여기에 instance의 등록·해제를 ECS가 자동으로 트리거하는 동작을 얹은 것이다.

Cloud Map 구성 요소DNS 구성 요소대응 근거
NamespacePrivate Hosted Zone (도메인)namespace 생성 시 대응하는 Route53 private hosted zone이 자동 생성된다
Service (= registry 역할)이름(hostname) + 레코드 타입·TTL 설정, 그 이름에 대한 레코드 세트service 이름 + DNS 설정으로 완성 이름이 만들어지고, registry로서 조회하면 등록된 엔드포인트 집합을 반환한다
Instance개별 A 레코드 (레코드 하나)instance = 레코드 하나이며, AWS_INSTANCE_IPV4 속성이 그 레코드의 IP 값이 된다

3 · 동작 흐름 — 등록 · 조회 · 재배포 시 갱신

핵심은 ECS 컨트롤 플레인(control plane)이 Task의 생성·소멸을 Cloud Map에 계속 반영한다는 점이다. 아래 흐름을 따른다(공식 문서 및 AWS 아키텍처 블로그).

  1. 등록(register) — ECS 서비스가 Task를 시작하면, ECS 컨트롤 플레인이 그 Task의 사설 IP를 Cloud Map service registry에 instance로 등록한다(AWS_INSTANCE_IPV4). Cloud Map은 private hosted zone에 대응하는 A 레코드를 만든다.
  2. 조회(discover) — 클라이언트는 claude-gw.internal.example.com이라는 고정된 이름을 VPC Route53 Resolver(10.0.0.2)로 조회한다. 헬시한 Task IP 집합이 반환된다.
  3. 소멸 시 등록 해제(deregister) — 새 버전 배포·크래시·재시작으로 Task가 사라지면, ECS 컨트롤 플레인이 등록 해제를 처리하고 Cloud Map은 해당 A 레코드를 삭제한다.
  4. 헬스 반영 — 헬스 체크를 통과하지 못한 엔드포인트는 DNS 응답에서 제외된다. 그래서 조회 결과에는 접속 가능한 Task만 남는다.
이 실습에서 달라지는 점 — zone을 손으로 만들지 않는다. Route53 Private Zone 설정 문서는 private hosted zone을 수동으로 만들고 A 레코드를 직접 채우는 방식이다. Service Discovery로 가면, private DNS namespace를 만들 때 Route53 private hosted zone이 자동 생성되므로 zone을 손으로 만들지 않는다. 즉 두 방식은 함께 쓰지 않는다 — Service Discovery를 쓰면 namespace(internal.example.com)와 service 이름(claude-gw)만 지정하고, A 레코드 채우기·갱신은 ECS가 자동으로 한다.
gateway도 postgres와 똑같이 Service Discovery를 켜야 한다. postgres Service를 만들 때만 Service Discovery를 켜고 gateway Service는 빠뜨리기 쉽다 — gateway가 RUNNING이어도 serviceRegistries가 빈 배열이면 Cloud Map에 전혀 등록되지 않아, 게이트웨이 hostname을 조회하면 NXDOMAIN이 난다. ECS 서비스 생성 후에는 service-registries를 나중에 추가할 수 없으므로(서비스를 재생성해야 한다), 생성 시점에 두 Service 모두 켜야 한다.
이미 같은 이름의 zone이 있으면 먼저 정리한다. private DNS namespace를 만들면 그 이름으로 Route53 private hosted zone이 자동 생성된다. 같은 VPC에 같은 도메인 이름의 zone이 이미 존재하면(예: Route53 Private Zone 설정 문서로 미리 수동 생성한 zone), 두 zone이 나란히 VPC에 연결돼 어느 쪽이 응답할지 보장되지 않는 split-brain 상태가 된다. namespace를 만들기 전에 기존 zone을 지우거나, 다른 도메인 이름을 쓴다.

4 · 설정 절차 (Console)

ECS 서비스를 만드는 화면에서 Service discovery 섹션을 켜면, private DNS namespace 생성 → service discovery service 생성 → 이 서비스에 연결까지 한 번에 처리된다(공식 문서: Create Service 워크플로는 private DNS namespace 등록만 지원한다).

  1. Clusters → 대상 클러스터 → Services 탭 → Create.
  2. Compute options = Launch type = Fargate.
  3. Service details
    • Task definition = 게이트웨이 task definition, Revision = 최신.
    • Service name = claude-gw.
    • Desired tasks = 1.
  4. Networking
    • VPC = 게이트웨이가 속한 VPC.
    • Subnets = Private Subnet.
    • Security group — ECS 클러스터 설정 5절과 동일한 기준으로 만든다.
    • Public IP = Disabled (Private Subnet이므로 공인 IP를 붙이지 않는다).
  5. Service discovery 섹션을 펼쳐 Use service discovery를 켠다.
    • Configure namespace = Create a new namespace, 네임스페이스 이름 = internal.example.com.
    • Service discovery name = claude-gw. (완성 이름이 claude-gw.internal.example.com이 된다.)
    • DNS record type = A. (Task가 awsvpc 네트워크 모드이므로 A 레코드를 쓴다.)
  6. Create. Task가 RUNNING이 되면 Cloud Map에 IP가 등록되고, internal.example.com private hosted zone이 자동 생성된다.

참고 — CLI로 할 경우

전체 절차는 ① private DNS namespace 생성 → ② service discovery service 생성 → ③ ECS 서비스에 연결이다. ①에서 만든 namespace ID를 ②가, ②에서 만든 service ARN을 ③이 참조한다. 

# ① private DNS namespace 생성 (Route53 private hosted zone이 자동 생성된다)
aws servicediscovery create-private-dns-namespace \
  --name internal.example.com \
  --vpc ${VPC_ID} \
  --region us-east-1
# → 반환된 OperationId로 get-operation 하면 namespace ID를 얻는다

# ② service discovery service 생성 (A 레코드, ECS 관리 헬스 체크)
aws servicediscovery create-service \
  --name claude-gw \
  --namespace-id ${NAMESPACE_ID} \
  --dns-config "NamespaceId=${NAMESPACE_ID},RoutingPolicy=MULTIVALUE,DnsRecords=[{Type=A,TTL=60}]" \
  --health-check-custom-config FailureThreshold=1 \
  --region us-east-1
# → 반환된 Service ARN을 다음 단계에서 쓴다

# ③ ECS 서비스 생성 시 --service-registries로 위 service를 연결
aws ecs create-service \
  --cluster <cluster> \
  --service-name claude-gw \
  --task-definition <gateway-taskdef> \
  --desired-count 1 \
  --launch-type FARGATE \
  --network-configuration "awsvpcConfiguration={subnets=[<private-subnet>],securityGroups=[<sg>],assignPublicIp=DISABLED}" \
  --service-registries "registryArn=${SERVICE_ARN}" \
  --region us-east-1
전제·제약 (공식 문서).
  • Fargate는 플랫폼 버전 1.1.0 이상에서 service discovery를 지원한다.
  • Task는 awsvpc·bridge·host 중 하나의 네트워크 모드여야 한다(none 불가). Fargate는 awsvpc이므로 A 레코드를 만들 수 있다.
  • 1절의 VPC DNS 속성(enableDnsSupport·enableDnsHostnames)이 켜져 있어야 resolution이 된다 — 수동 zone 방식과 동일한 요구사항이다.
  • service discovery로 만든 Cloud Map 리소스는 수동으로 정리해야 한다(서비스 삭제 시 자동 삭제되지 않는다).
  • service당 Task는 최대 1,000개(Route53 쿼터). 이 실습은 게이트웨이 1개이므로 여유롭다.

5 · resolve 확인

Client VPN으로 VPC에 들어온 상태(단계 4)에서, 고정된 이름이 현재 Task의 사설 IP로 풀리는지 확인한다. 재배포 뒤 다시 조회하면 IP만 바뀌고 이름은 그대로다. 

nslookup claude-gw.internal.example.com
# → 현재 살아 있는 Task의 사설 IP(10.0.x.x)가 나와야 정상
#   재배포 후 다시 조회하면 새 Task의 IP로 바뀌어 있다

Client VPN 설정 — 인증서 · 엔드포인트 · 접속

랩탑을 VPC 사설망에 넣어, 랩탑의 CLI·브라우저가 Private Subnet의 게이트웨이에 도달하게 한다.

실습 가이드의 단계 3에서 참조하는 문서다. 게이트웨이는 사설 IP로만 접근을 허용하므로, VPC 밖의 랩탑은 그대로는 게이트웨이에 닿을 수 없다. AWS Client VPN으로 랩탑을 VPC 사설망에 편입시켜 이 경로를 연다. 이 문서는 인증서 생성 → 엔드포인트 구성 → 랩탑 접속을 순서대로 다룬다.

이 문서는 mutual TLS 인증 방식을 쓴다. Client VPN은 여러 인증 방식을 지원하지만, 여기서는 가장 단순한 상호 인증(mutual authentication)을 쓴다. 클라이언트와 엔드포인트가 서로 인증서로 신원을 증명하는 방식이다. 서버 인증서는 반드시 ACM에 업로드해야 하고, 클라이언트 인증서는 같은 CA로 발급하면 별도 업로드가 필요 없다.

1 · 인증서 생성 (easy-rsa)

OpenVPN의 easy-rsa로 CA를 만들고 서버·클라이언트 인증서를 발급한다. macOS·Linux 기준이다. 

# easy-rsa 받기
git clone https://github.com/OpenVPN/easy-rsa.git
cd easy-rsa/easyrsa3

# PKI 초기화 + CA 생성 (nopass: 키 암호 없이)
./easyrsa init-pki
./easyrsa build-ca nopass

# 서버 인증서·키
./easyrsa --san=DNS:server build-server-full server nopass

# 클라이언트 인증서·키 (연결할 사용자마다 하나씩 — 여기선 1개)
./easyrsa build-client-full client1.domain.tld nopass

# 필요한 파일을 한 폴더로 모으기
mkdir -p ~/client-vpn
cp pki/ca.crt                        ~/client-vpn/
cp pki/issued/server.crt             ~/client-vpn/
cp pki/private/server.key            ~/client-vpn/
cp pki/issued/client1.domain.tld.crt ~/client-vpn/
cp pki/private/client1.domain.tld.key ~/client-vpn/
인증서 제약 두 가지(공식 문서). Client VPN 엔드포인트는 RSA 1024/2048비트 키만 지원하고, 클라이언트 인증서는 Subject에 CN 속성이 있어야 한다. easy-rsa 기본값이 이를 충족하므로 위 절차를 그대로 따르면 된다.

2 · 서버 인증서를 ACM에 업로드

서버 인증서는 엔드포인트와 같은 리전(us-east-1)의 ACM에 있어야 한다. 클라이언트 인증서를 같은 CA로 발급했으므로 클라이언트 쪽은 업로드하지 않아도 된다. 

aws acm import-certificate --region us-east-1 \
  --certificate      fileb://~/client-vpn/server.crt \
  --private-key      fileb://~/client-vpn/server.key \
  --certificate-chain fileb://~/client-vpn/ca.crt

출력된 인증서 ARN을 메모한다 — 다음 단계에서 엔드포인트가 이 ARN을 참조한다.

3 · Client VPN 엔드포인트 생성

  1. 클라이언트 CIDR — 단계 0의 값 172.16.0.0/22. VPC CIDR과 겹치지 않고, /22 이상이어야 한다.
  2. 인증: mutual TLS — 서버 인증서 ARN(2단계)을 지정한다. 클라이언트 인증서 ARN도 같은 서버 인증서 ARN을 쓰면 된다(같은 CA 발급).
  3. Enable split-tunnel을 체크한다. 기본값(꺼짐)으로 두면 풀 터널이 되어, 랩탑의 인터넷 목적지 트래픽(Cognito 로그인 화면 등)까지 전부 VPN으로 잡힌다. 이 엔드포인트의 Authorization rule·route table은 VPC CIDR만 허용하므로, 풀 터널 상태에서는 그 인터넷 트래픽이 조용히 드롭돼 디바이스 인증 코드를 입력해도 반응이 없는 증상으로 나타난다(아래 5단계 callout에 상세 설명). 생성 화면에서 놓쳤다면 Actions → Modify client VPN endpoint에서 나중에 켤 수 있지만, 그 경우 기존 연결을 끊고 재연결해야 새 라우팅이 반영된다.
  4. 연결 로그 — 테스트면 비활성화해도 된다.

4 · 엔드포인트를 서브넷·규칙과 연결

  1. Target network 연결(associate) — 엔드포인트를 단계 2의 Private Subnet에 연결한다. 단일 AZ면 서브넷 하나로 충분하다.
  2. Authorization rule — 클라이언트가 VPC CIDR(10.0.0.0/16)에 접근하도록 허용한다. 이 규칙이 없으면 연결돼도 트래픽이 막힌다.
  3. DNS 서버 — 엔드포인트 DNS를 VPC Route53 Resolver(10.0.0.2)로 지정한다. 이래야 랩탑이 VPN 연결 중 private hosted zone의 게이트웨이 hostname을 사설 IP로 resolve한다.
DNS 지정이 게이트웨이 접속의 핵심이다. 게이트웨이 hostname은 private hosted zone에만 있다. 엔드포인트 DNS를 VPC Resolver로 지정하지 않으면, VPN이 연결돼도 랩탑이 게이트웨이 이름을 사설 IP로 풀지 못해 CLI·브라우저가 접속하지 못한다. 이 항목이 Client VPN 설정에서 가장 자주 누락되는 지점이다.

5 · 랩탑에서 접속

  1. 클라이언트 설정(.ovpn)을 내려받는다. VPC 콘솔의 Client VPN endpoints에서 엔드포인트를 선택하고 Download client configuration을 누르거나, CLI로 내보낸다. 
    aws ec2 export-client-vpn-client-configuration \
  --client-vpn-endpoint-id cvpn-endpoint-0011abc... \
  --output text > ~/client-vpn/client-config.ovpn
  2. 내려받은 .ovpn에 클라이언트 인증서·키를 추가한다. 콘솔·CLI에서 받은 파일에는 CA(<ca>…</ca>)만 들어 있고 클라이언트 인증서·키는 비어 있으므로, mutual TLS에서는 이 둘을 직접 넣어야 연결된다. 파일 끝에 <cert>…</cert>로 client1.domain.tld.crt의 내용을, <key>…</key>로 client1.domain.tld.key의 내용을 붙여 넣는다. 
    <cert>
client1.domain.tld.crt 파일 내용
</cert>

<key>
client1.domain.tld.key 파일 내용
</key>
    인증서(.crt)는 -----BEGIN CERTIFICATE-----부터 -----END CERTIFICATE-----까지 전체를 넣는다.
  3. AWS VPN Client 앱을 설치하고, File → Manage Profiles → Add Profile에서 위 .ovpn을 프로파일로 등록한 뒤 Connect한다.
split-tunnel은 앱이 아니라 엔드포인트 설정이다. split-tunnel을 켜면 엔드포인트 route table의 경로(여기서는 VPC 10.0.0.0/16)만 랩탑으로 push돼 그 대상만 VPN을 타고, 나머지 인터넷 트래픽은 로컬로 나간다. 켜지 않으면 기본값(full-tunnel)이라 랩탑의 0.0.0.0/0 전 트래픽이 VPN으로 흐른다. 이 옵션은 3단계의 엔드포인트 생성 화면(또는 Actions → Modify client VPN endpoint)에서 켠다 — AWS VPN Client 앱에는 이 토글이 없다. 실습에서는 켜 두기를 권장한다.

빠뜨렸을 때 실제로 나타나는 증상: nslookup은 정상 동작하고(VPC 대상 트래픽이라 문제없음) VPN도 Connected로 표시되며, 게이트웨이의 디바이스 인증 화면도 정상적으로 열린다. 다만 코드를 제출하면 게이트웨이가 Cognito(퍼블릭 인터넷) 로그인 화면으로 리다이렉트를 지시하는데, 그 트래픽이 풀 터널에 잡혀 인터넷으로 나가지 못하고 조용히 드롭된다 — 그래서 브라우저가 그냥 멈춘 것처럼 보인다. 게이트웨이 로그에는 device.verify가 result: "redirect"로 정상 응답한 기록만 남아, 게이트웨이 자체는 문제가 없다는 것을 보여준다.

6 · 접속 확인

AWS VPN Client 앱(5단계에서 .ovpn 프로파일로 연결한 그 데스크톱 앱)에 표시되는 Connected는 OpenVPN 제어 채널(control channel)이 열렸다는 것만 뜻한다. 구체적으로는 클라이언트와 엔드포인트 사이의 mutual TLS 핸드셰이크가 성공하고, 데이터 채널(data channel)이 협상되어, 랩탑이 클라이언트 CIDR(172.16.0.0/22)에서 IP를 할당받은 상태다. 여기까지는 인증서와 TLS 계층이 정상이라는 의미일 뿐, 그 위로 실제 트래픽이 목적지까지 전달되는지는 보장하지 않는다.

데이터 평면(data plane)의 전달은 별개의 세 조건에 달려 있고, 이들은 Connected 여부와 무관하게 실패할 수 있다: ① 엔드포인트의 route table에 목적지 CIDR로 가는 경로가 있어 클라이언트에 push되는지, ② Authorization rule이 그 목적지 CIDR을 허용하는지, ③ 엔드포인트가 DNS 서버(10.0.0.2)를 클라이언트에 push하는지. 이 중 하나라도 빠지면 Connected 상태에서도 질의·연결이 조용히 실패한다. 그래서 아래를 순서대로 확인한다.

6-1 · 랩탑이 VPN IP를 받았는지

클라이언트 CIDR(172.16.0.0/22)에서 주소를 받았는지 확인한다.

ifconfig | grep 172.16       # macOS · Linux
# → utun 인터페이스에 172.16.x.x 가 보이면 정상

6-2 · 게이트웨이 Task 배포 전 — private zone까지 경로가 살아 있는지

게이트웨이 hostname의 A 레코드는 게이트웨이 Task 배포 후(실습 가이드 단계 5) 사설 IP로 채운다. 아직 A 레코드가 없어도, 단계 2에서 만든 private hosted zone에는 SOA 레코드가 기본으로 존재한다. 이걸 조회하면 DNS 서버 지정(10.0.0.2) + private zone이 VPC에 연결됨 + VPC로 트래픽이 도달함을 한 번에 검증할 수 있다. 

nslookup -type=SOA internal.example.com 10.0.0.2
# internal.example.com = 게이트웨이 hostname 전체가 아니라 그 부모 도메인(zone 이름)
# → ns-...awsdns... 형태의 SOA 가 나오면 경로가 완전히 살아 있는 것
Resolver(10.0.0.2)는 ping에 응답하지 않는다. Resolver는 DNS 질의에만 응답하고 ICMP에는 응답하지 않으므로 ping 10.0.0.2로는 확인할 수 없다. 위 SOA 질의가 10.0.0.2를 통해 응답을 받는 것 자체가 Authorization rule과 라우팅이 동작한다는 증거다.

6-3 · 게이트웨이 Task 배포 후 — 사설 IP로 풀리는지 (최종 확인)

단계 5에서 A 레코드를 채운 뒤, 게이트웨이 hostname 전체가 사설 IP로 풀리는지 확인한다. 이게 되면 실습 가이드 단계 7의 로그인 테스트로 넘어간다. 

nslookup claude-gw.internal.example.com
# claude-gw.internal.example.com = 단계 0에서 정한 hostname (zone 이름 + 레코드 이름 claude-gw)
# → 10.0.x.x 사설 IP가 나와야 정상
막히면 여기부터.
  • 앱은 Connected인데 nslookup이 connection timed out; no servers could be reached → VPC 안으로 트래픽이 도달하지 못하고 있다. 다음을 순서대로 확인한다.
    1. DNS 서버를 명시해 다시 질의한다 — nslookup -type=SOA internal.example.com 10.0.0.2. 이건 응답하는데 서버 없이 던진 질의만 실패하면, 랩탑에 DNS 10.0.0.2가 push되지 않은 것이다(엔드포인트 DNS 미지정, 4단계 확인).
    2. VPC CIDR로 가는 경로가 있는지 — netstat -rn | grep '10\.0'. 10.0.0.0/16이 utun 인터페이스로 잡혀 있어야 한다. 없으면 split-tunnel 엔드포인트 route table에 VPC 경로가 없는 것이다(5단계 callout).
    3. Authorization rule이 있는지 (이 증상의 가장 흔한 원인) — 엔드포인트의 Authorization rules 탭에 VPC CIDR(10.0.0.0/16) 허용이 있어야 한다. 없으면 Connected여도 VPC 내부로 가는 모든 트래픽(10.0.0.2 포함)이 조용히 드롭돼 정확히 이 타임아웃이 난다(4단계 Authorization rule).
  • SOA·서버는 응답하는데 hostname이 사설 IP로 안 풀림 → private hosted zone의 A 레코드(실습 가이드 단계 5에서 채움)가 아직 없거나 이름이 틀린 것이다. zone 이름 + 레코드 이름 claude-gw가 합쳐져 완성 이름이 되는지 확인한다.
  • 이름은 풀리는데 게이트웨이에 접근 불가 → gateway 보안 그룹이 postgres SG를 잘못 재사용하고 있지 않은지, 실제로 클라이언트 CIDR의 443을 허용하는지 확인한다. 보안 그룹은 맞는데 ECONNREFUSED가 나면 게이트웨이의 listen.port가 443인지 확인한다.
  • 연결·DNS·SG는 다 정상인데 디바이스 인증 코드 입력 후 반응 없음 → split-tunnel이 꺼져 있어 Cognito(인터넷) 트래픽이 드롭되는 경우다. 위 5단계 callout대로 split-tunnel을 켜고 재연결한다.
  • 연결 자체가 실패(Connected가 안 뜸) → .ovpn에 클라이언트 인증서·키를 넣었는지, ACM 서버 인증서가 us-east-1에 있는지 확인한다.

이 문서의 설정을 실제로 적용하며 마주친 문제(split-tunnel 누락, 보안 그룹 재사용)는 트러블슈팅 로그에 순서대로 기록돼 있다.

Client VPN 설정 — 인증서 · 엔드포인트 · 접속

랩탑을 VPC 사설망에 넣어, 랩탑의 CLI·브라우저가 Private Subnet의 게이트웨이에 도달하게 한다.

실습 가이드의 단계 3에서 참조하는 문서다. 게이트웨이는 사설 IP로만 접근을 허용하므로, VPC 밖의 랩탑은 그대로는 게이트웨이에 닿을 수 없다. AWS Client VPN으로 랩탑을 VPC 사설망에 편입시켜 이 경로를 연다. 이 문서는 인증서 생성 → 엔드포인트 구성 → 랩탑 접속을 순서대로 다룬다.

이 문서는 mutual TLS 인증 방식을 쓴다. Client VPN은 여러 인증 방식을 지원하지만, 여기서는 가장 단순한 상호 인증(mutual authentication)을 쓴다. 클라이언트와 엔드포인트가 서로 인증서로 신원을 증명하는 방식이다. 서버 인증서는 반드시 ACM에 업로드해야 하고, 클라이언트 인증서는 같은 CA로 발급하면 별도 업로드가 필요 없다.

1 · 인증서 생성 (easy-rsa)

OpenVPN의 easy-rsa로 CA를 만들고 서버·클라이언트 인증서를 발급한다. macOS·Linux 기준이다. 

# easy-rsa 받기
git clone https://github.com/OpenVPN/easy-rsa.git
cd easy-rsa/easyrsa3

# PKI 초기화 + CA 생성 (nopass: 키 암호 없이)
./easyrsa init-pki
./easyrsa build-ca nopass

# 서버 인증서·키
./easyrsa --san=DNS:server build-server-full server nopass

# 클라이언트 인증서·키 (연결할 사용자마다 하나씩 — 여기선 1개)
./easyrsa build-client-full client1.domain.tld nopass

# 필요한 파일을 한 폴더로 모으기
mkdir -p ~/client-vpn
cp pki/ca.crt                        ~/client-vpn/
cp pki/issued/server.crt             ~/client-vpn/
cp pki/private/server.key            ~/client-vpn/
cp pki/issued/client1.domain.tld.crt ~/client-vpn/
cp pki/private/client1.domain.tld.key ~/client-vpn/
인증서 제약 두 가지(공식 문서). Client VPN 엔드포인트는 RSA 1024/2048비트 키만 지원하고, 클라이언트 인증서는 Subject에 CN 속성이 있어야 한다. easy-rsa 기본값이 이를 충족하므로 위 절차를 그대로 따르면 된다.

2 · 서버 인증서를 ACM에 업로드

서버 인증서는 엔드포인트와 같은 리전(us-east-1)의 ACM에 있어야 한다. 클라이언트 인증서를 같은 CA로 발급했으므로 클라이언트 쪽은 업로드하지 않아도 된다. 

aws acm import-certificate --region us-east-1 \
  --certificate      fileb://~/client-vpn/server.crt \
  --private-key      fileb://~/client-vpn/server.key \
  --certificate-chain fileb://~/client-vpn/ca.crt

출력된 인증서 ARN을 메모한다 — 다음 단계에서 엔드포인트가 이 ARN을 참조한다.

3 · Client VPN 엔드포인트 생성

  1. 클라이언트 CIDR — 단계 0의 값 172.16.0.0/22. VPC CIDR과 겹치지 않고, /22 이상이어야 한다.
  2. 인증: mutual TLS — 서버 인증서 ARN(2단계)을 지정한다. 클라이언트 인증서 ARN도 같은 서버 인증서 ARN을 쓰면 된다(같은 CA 발급).
  3. 연결 로그 — 테스트면 비활성화해도 된다.

4 · 엔드포인트를 서브넷·규칙과 연결

  1. Target network 연결(associate) — 엔드포인트를 단계 2의 Private Subnet에 연결한다. 단일 AZ면 서브넷 하나로 충분하다.
  2. Authorization rule — 클라이언트가 VPC CIDR(10.0.0.0/16)에 접근하도록 허용한다. 이 규칙이 없으면 연결돼도 트래픽이 막힌다.
  3. DNS 서버 — 엔드포인트 DNS를 VPC Route53 Resolver(10.0.0.2)로 지정한다. 이래야 랩탑이 VPN 연결 중 private hosted zone의 게이트웨이 hostname을 사설 IP로 resolve한다.
DNS 지정이 게이트웨이 접속의 핵심이다. 게이트웨이 hostname은 private hosted zone에만 있다. 엔드포인트 DNS를 VPC Resolver로 지정하지 않으면, VPN이 연결돼도 랩탑이 게이트웨이 이름을 사설 IP로 풀지 못해 CLI·브라우저가 접속하지 못한다. 이 항목이 Client VPN 설정에서 가장 자주 누락되는 지점이다.

5 · 랩탑에서 접속

  1. 클라이언트 설정(.ovpn)을 내려받는다. VPC 콘솔의 Client VPN endpoints에서 엔드포인트를 선택하고 Download client configuration을 누르거나, CLI로 내보낸다. 
    aws ec2 export-client-vpn-client-configuration \
  --client-vpn-endpoint-id cvpn-endpoint-0011abc... \
  --output text > ~/client-vpn/client-config.ovpn
  2. 내려받은 .ovpn에 클라이언트 인증서·키를 추가한다. 콘솔·CLI에서 받은 파일에는 CA(<ca>…</ca>)만 들어 있고 클라이언트 인증서·키는 비어 있으므로, mutual TLS에서는 이 둘을 직접 넣어야 연결된다. 파일 끝에 <cert>…</cert>로 client1.domain.tld.crt의 내용을, <key>…</key>로 client1.domain.tld.key의 내용을 붙여 넣는다. 
    <cert>
client1.domain.tld.crt 파일 내용
</cert>

<key>
client1.domain.tld.key 파일 내용
</key>
    인증서(.crt)는 -----BEGIN CERTIFICATE-----부터 -----END CERTIFICATE-----까지 전체를 넣는다.
  3. AWS VPN Client 앱을 설치하고, File → Manage Profiles → Add Profile에서 위 .ovpn을 프로파일로 등록한 뒤 Connect한다.
split-tunnel은 앱이 아니라 엔드포인트 설정이다. split-tunnel을 켜면 엔드포인트 route table의 경로(여기서는 VPC 10.0.0.0/16)만 랩탑으로 push돼 그 대상만 VPN을 타고, 나머지 인터넷 트래픽은 로컬로 나간다. 켜지 않으면 기본값(full-tunnel)이라 랩탑의 0.0.0.0/0 전 트래픽이 VPN으로 흐른다. 이 옵션은 3단계의 엔드포인트 생성 화면(또는 Actions → Modify client VPN endpoint)에서 켠다 — AWS VPN Client 앱에는 이 토글이 없다. 실습에서는 켜 두기를 권장한다.

6 · 접속 확인

VPN 연결 후, 게이트웨이 hostname이 사설 IP로 풀리는지 확인한다. 이게 되면 실습 가이드 단계 7의 로그인 테스트로 넘어간다. 

nslookup <gateway-hostname>
# → 10.0.x.x 사설 IP가 나와야 정상
막히면 여기부터.
  • hostname이 사설 IP로 안 풀림 → 4단계의 DNS 서버 지정, 그리고 private hosted zone의 A 레코드(실습 가이드 단계 5에서 채움)를 확인한다.
  • 연결은 됐는데 게이트웨이에 접근 불가 → Authorization rule에 VPC CIDR 허용이 있는지, gateway 보안 그룹이 클라이언트 CIDR의 443을 허용하는지 확인한다.
  • 연결 자체가 실패 → .ovpn에 클라이언트 인증서·키를 넣었는지, ACM 서버 인증서가 us-east-1에 있는지 확인한다.

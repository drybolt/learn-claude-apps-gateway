Lesson 3 · 작동 방식

작동 방식

로그인부터 추론 요청, 세션 만료까지의 다섯 단계.

Lesson 2에서 gateway.yaml의 각 설정 블록이 맡는 역할을 보았다. 여기서는 그 블록들이 실제 요청 하나를 처리할 때 어떤 순서로 협력하는지를 다섯 단계로 설명한다. 먼저 아래 흐름도로 전체 그림을 훑은 뒤, 이어지는 절에서 각 단계를 하나씩 살펴본다.

1단계. 로그인 (디바이스 인증 플로우)

개발자가 터미널에서 /login을 실행하면, CLI와 브라우저가 각자 다른 일을 맡는 디바이스 인증 플로우(RFC 8628 device authorization grant)가 시작된다. 게이트웨이가 내려준 확인 URL을 개발자가 브라우저에서 열어 사용자 코드를 입력하면, 게이트웨이는 브라우저에 회사 IdP 로그인 화면으로 이동하라는 응답을 보내고, 브라우저는 그 응답에 따라 스스로 이동해 로그인 화면을 띄운다. 그동안 CLI는 짧은 간격으로 로그인 완료 여부를 물으며 대기한다(polling). 코드 발급·리다이렉트·콜백이 실제로 어떻게 이뤄지는지는 디바이스 인증·로그인·세션 확립 자세히에서 다룬다.

2단계. 세션 확립

IdP 로그인이 끝나면 게이트웨이가 세션 토큰(JWT)을 발급하고 로그인 상태를 PostgreSQL에 기록한다. polling 중이던 CLI는 이 토큰을 받아 대기를 끝내고, 이 시점 이후로는 원본 IdP 자격증명이 아니라 이 세션 토큰만으로 게이트웨이와 통신한다. id_token 검증과 이메일·그룹 추출 같은 상세 과정은 디바이스 인증·로그인·세션 확립 자세히에서 다룬다.

3단계. 요청별 정책 적용

CLI가 무언가를 요청할 때마다 세션 토큰이 함께 전송된다. 게이트웨이는 토큰에 담긴 사용자의 IdP 그룹을 managed.policies의 match 조건과 대조해 이 사용자에게 적용할 정책을 결정한다. 이 정책이 모델 allowlist, 툴 권한, 환경변수 등을 정한다. 정책은 매 요청마다 다시 계산되는 것이 아니라 로그인 시점과 이후 1시간 주기의 갱신 시점에 클라이언트로 전달되고, 클라이언트가 그 정책을 따른다.

정책을 담는 두 파일 — managed-settings.json vs remote-settings.json. 관리자 정책을 개발자 기기에 전달하는 경로는 두 가지이고, 이름이 비슷하지만 성격이 다르다.

managed-settings.json (정적 · 기기 단위) — 관리자가 MDM(기기 관리 도구)으로 각 기기의 고정 경로(macOS /Library/Application Support/ClaudeCode/managed-settings.json, Linux/WSL /etc/claude-code/managed-settings.json, Windows C:\Program Files\ClaudeCode\managed-settings.json)에 미리 배포하는 파일이다. 게이트웨이 없이도 쓰지만, 정책이 기기에 묶여 그 기기를 누가 쓰든 같은 정책이 적용되고, 바꾸려면 MDM으로 다시 배포해야 한다.

remote-settings.json (동적 · 사용자 단위) — 로그인 시 게이트웨이가 사용자의 IdP 그룹에 맞는 정책을 클라이언트로 내려주면 CLI가 ~/.claude/remote-settings.json에 캐시하는 파일이다. 정책이 사용자(그룹)에 묶여, 같은 기기라도 로그인한 사람에 따라 다른 정책이 적용되고, 로그인·갱신 때마다 최신 정책을 다시 받는다. 이 캐시는 사용자 로컬의 ~/.claude/settings.json보다 우선 적용되므로 개발자가 관리자 정책을 덮어쓸 수 없다.

게이트웨이 방식이 등장한 이유가 바로 이 차이다. 순수 Bedrock 환경에서는 managed-settings.json의 기기 단위 정적 배포만 가능했는데, 게이트웨이는 이를 사용자 단위 동적 전달로 확장한다. 관리자가 gateway.yaml의 managed 블록에 그룹별 정책을 어떻게 적는지는 gateway.yaml 설정 구조의 선택 블록 절에서 다룬다.

4단계. 추론 요청 전달

개발자가 실제로 Claude Code에 질문하면 CLI는 항상 동일한 Anthropic Messages API 형식으로, 2단계에서 발급받은 세션 토큰을 Authorization: Bearer 헤더에 실어 게이트웨이에 요청을 보낸다. 게이트웨이는 이 요청이 정책상 허용된 모델인지(managed.policies[].cli.availableModels) 먼저 검사하고, 허용되지 않으면 400 응답을 돌려준다. 통과하면 upstreams에 등록된 대상에 맞는 형식으로 번역해 전달하고, 응답이 오면 다시 CLI가 이해하는 형식으로 돌려준다. 이 과정에서 CLI는 요청이 어느 업스트림으로 갔는지 알 필요가 없으며, 번역과 라우팅은 전부 게이트웨이가 대신한다.

"번역"이 실제로 바꾸는 것. CLI가 보내는 Anthropic Messages API 형식과 Bedrock의 InvokeModel API를 비교하면, 요청 바디의 필드(messages, system, max_tokens 등)는 대부분 그대로다. 차이는 두 가지뿐이다 — ① 최상위 model 필드가 바디 안에 없고 InvokeModel 호출 자체의 modelId 파라미터로 대신 지정되며, ② Bedrock 전용 필드 anthropic_version: "bedrock-2023-05-31"이 추가로 필요하다.

Messages API가 지원하는 인증 방식은 API 키 하나만이 아니다. x-api-key(ANTHROPIC_API_KEY) 외에도 OAuth Bearer 토큰(Authorization: Bearer) — 구독 로그인(/login), ANTHROPIC_AUTH_TOKEN, Workload Identity Federation 등 — 을 지원한다. API 키는 여러 인증 방식 중 하나일 뿐이다.

Bedrock도 InvokeModel만 쓰지 않는다. AWS는 두 엔드포인트를 제공한다 — 고전 bedrock-runtime(InvokeModel·Converse, AWS SigV4 또는 최근엔 Bedrock API 키도 지원)과 신규 bedrock-mantle(Messages API 형식을 그대로 받는다 — anthropic_version 바디 필드 없이 HTTP 헤더로만 처리, Bedrock API 키 또는 SigV4). 즉 bedrock-mantle에서는 "Bedrock=다른 형식"이라는 전제 자체가 성립하지 않는다.

이 실습이 쓰는 조합. 이 실습의 gateway.yaml은 upstreams.auth: {}로 비워 뒀다. 즉 게이트웨이가 실행되는 환경(이 실습에서는 ECS)의 AWS 자격증명 체인을 그대로 쓰므로, 실제 자격증명은 ECS Task Role이다. 이는 위에서 설명한 고전 bedrock-runtime + AWS SigV4 조합에 해당한다.

이 조합에서 구간별 인증은 서로 다른 두 값을 쓴다. CLI ↔ 게이트웨이 구간은 2단계에서 발급한 세션 토큰(JWT)으로 인증한다. 헤더 형식은 위에서 말한 Messages API의 Authorization: Bearer를 그대로 쓰지만, 담긴 값은 Anthropic의 OAuth 토큰이 아니라 이 게이트웨이가 발급한 자체 세션 토큰이다. 게이트웨이 ↔ Bedrock 구간은 실행 환경의 AWS 자격증명(이 실습에서는 ECS Task Role) + SigV4로 인증한다. 게이트웨이가 CLI의 요청을 받아 이 형식·인증으로 바꿔 직접 호출하고, 응답을 다시 Messages API 형식으로 바꿔 돌려준다. 이 변환을 게이트웨이 자신이 수행하므로 CLI는 업스트림이 무엇인지 알 필요가 없다.

5단계. 세션 만료와 재로그인

세션 토큰은 ttl_hours가 지나면 만료된다. 만료되기 전에 CLI가 조용히 토큰 갱신을 시도하는데, 이때 게이트웨이는 IdP에 사용자가 여전히 유효한지 재확인한다. IdP에서 계정이 비활성화되었다면 이 갱신이 실패하고, 개발자는 다시 브라우저 로그인을 해야 한다. 결과적으로 권한 회수는 IdP에서 계정을 끄는 것만으로 이루어지고, 게이트웨이가 그것을 다음 갱신 시점에 자동으로 반영한다.

"조용히"의 기술적 의미 — 리프레시 토큰 그랜트(refresh token grant)로, 사용자 상호작용이 없는 서버 대 서버 호출이다. 일반 로그인은 브라우저 리다이렉트(302)를 거쳐 사용자가 IdP 로그인 화면에서 자격증명을 입력하는 authorization code flow다(브라우저 리다이렉트 → IdP 로그인 → 콜백, Lesson 4의 5~7단계 다이어그램 참조). 이건 사용자 액션이 필수다. 반면 세션이 만료되기 전에 시도되는 갱신(정확한 시점은 공개되지 않음)은 이 흐름을 전혀 타지 않는다. 1단계에서 게이트웨이는 id_token과 함께 리프레시 토큰도 받아 저장해 두는데(Lesson 4), 만료가 다가오면 게이트웨이는 브라우저에 아무것도 띄우지 않고 이 리프레시 토큰을 들고 IdP의 토큰 엔드포인트에 직접 HTTP 요청을 보낸다(OAuth 2.0의 grant_type=refresh_token 요청). IdP는 계정이 여전히 활성 상태인지 확인한 뒤, 유효하면 새 id_token(+ 새 리프레시 토큰)을 돌려주고, 게이트웨이는 이 응답으로 새 세션 토큰(JWT)을 발급한다. 이 전체 과정이 서버 대 서버 HTTP 요청 하나로 끝나므로 브라우저 리다이렉트나 사용자 입력이 전혀 개입하지 않는다 — 이것이 "조용히"가 가리키는 정확한 동작이다.

IdP가 계정을 비활성화했다면, 리프레시 토큰도 그 계정에 연결돼 있으므로 이 토큰 엔드포인트 요청 자체가 거부된다. 이때만 게이트웨이가 서버 대 서버 갱신을 포기하고, 처음으로 브라우저를 통한 authorization code flow(사용자 개입 필요)로 되돌아간다. 즉 "조용히"는 정확히 "리프레시 토큰 그랜트 경로"를, 그 반대는 "authorization code 그랜트 경로(사용자 로그인 화면)"를 가리킨다.

Lesson 4 · 심화

디바이스 인증·로그인·세션 확립 자세히

디바이스 코드 발급부터 세션 토큰 발급까지의 열 단계.

게이트웨이 로그인에서 가장 헷갈리는 지점은 "인증 안 된 요청이 IdP로 리다이렉트된다"는 웹 앱의 통념이 여기서는 맞지 않는다는 것이다. 게이트웨이는 디바이스 인증 플로우(RFC 8628 device authorization grant)를 쓰며, 여기서는 CLI(Claude Code)와 브라우저가 서로 다른 주체로 분리되어 각자 다른 일을 한다. 아래 다이어그램은 네 주체(CLI · 게이트웨이 · 브라우저 · IdP)가 시간 순으로 주고받는 것을 보여준다.

단계별 설명

1~2. CLI ↔ 게이트웨이: 디바이스 코드 발급

개발자가 /login을 실행하면 CLI가 게이트웨이에 디바이스 인증을 요청한다(1). 게이트웨이는 CLI가 polling에 쓸 디바이스 코드(device_code), 개발자가 브라우저에 입력할 짧은 사용자 코드(user_code), 그리고 확인용 URL(verification_uri)을 돌려준다(2). 여기서 CLI는 브라우저로 리다이렉트하지 않는다 — 이 점이 웹 앱 SSO와 다른 핵심이다. 일반 웹 앱은 접근 주체가 곧 브라우저라 서버가 그 브라우저를 바로 IdP로 리다이렉트하면 되지만, 터미널에서 실행되는 CLI에는 리다이렉트할 브라우저가 없다. 그래서 게이트웨이는 CLI에 위의 세 값만 돌려주고, CLI는 그 자리에서 대기하며 로그인이 끝나기를 기다린다(아래 polling callout 참고). 이렇게 CLI와 브라우저를 나누면 둘이 서로 다른 기기에서 실행되어도 되는 이점이 생기는데, 이는 문서 끝의 "왜 CLI와 브라우저를 분리하는가" callout에서 다룬다.

2단계 응답에 담기는 값(RFC 8628). device_code는 CLI만 쓰는 값으로, 토큰 엔드포인트(CLI가 액세스 토큰을 받아가는 게이트웨이의 OAuth 주소)를 polling할 때 자신의 대기를 식별한다(개발자에게 노출되지 않는다). user_code는 사람이 브라우저 확인 페이지에 입력하는 값이라 짧고 읽기 쉬운 형태로 발급된다(Claude Apps Gateway는 20자 알파벳에서 뽑은 8자를 쓰고, 10분 뒤 만료된다). verification_uri는 그 user_code를 입력할 페이지 주소다. 이 밖에 코드 만료 시간(expires_in)과 polling 최소 간격(interval)도 함께 내려온다.
polling. CLI는 대기만 한다. 2단계 이후 CLI가 하는 일은 "로그인이 끝났는지"를 짧은 간격으로 게이트웨이에 계속 물어보는 것뿐이다(다이어그램의 파란 세로 막대). 실제 로그인은 아래 브라우저 구간에서 진행되고, CLI는 그 결과를 기다린다.

3~4. 브라우저: 확인 페이지 접근

개발자가 2단계에서 받은 확인 URL을 브라우저에서 연다(3). 브라우저가 게이트웨이의 확인 페이지에 접근하면(4), 개발자는 이 페이지에 2단계에서 받은 사용자 코드(user_code)를 입력한다.

이때 두 코드의 역할이 갈린다. device_code는 CLI 쪽을 식별하는 값이라 CLI만 들고 토큰 엔드포인트 polling에 쓰고, 브라우저는 이 값을 갖고 있지 않다. user_code는 브라우저 쪽이 제출하는 값이다. 그래서 게이트웨이는 지금 마주한 이 브라우저 세션이 어느 CLI의 대기와 짝인지, 브라우저가 방금 제출한 user_code를 키로 저장된 디바이스 인증 레코드(PostgreSQL)를 조회해 알아낸다. 조회로 찾은 device_code가 그 짝이며, 이 연결을 통해 IdP 로그인이 끝난 결과가 올바른 CLI의 polling 응답으로 전달된다.

5. 게이트웨이 → IdP: 브라우저를 리다이렉트

게이트웨이가 브라우저를 IdP로 리다이렉트한다(5). 이때 목적지는 issuer URL 자체가 아니라, issuer가 서빙하는 discovery 문서(/.well-known/openid-configuration) 안에 적힌 authorization_endpoint다. 게이트웨이는 부팅 시 OIDC discovery로 이 주소를 미리 알아둔 상태다. 즉 issuer는 "실제 리다이렉트 주소를 찾아내는 출발점"이지, 그 자체가 목적지가 아니다.

"리다이렉트한다"는 것은 구체적으로 무엇인가

먼저 이 단계가 풀어야 하는 문제부터 보자. 게이트웨이 앞에 브라우저가 와 있지만(개발자가 확인 URL을 열었으니까), 게이트웨이는 이 사람을 로그인시킬 수 없다. 로그인은 회사 IdP만 할 수 있는 일이고, 게이트웨이는 그 사람의 비밀번호를 모르며 대신 입력해 줄 수도 없다. 그래서 게이트웨이가 할 수 있는 최선은 "당신을 로그인시켜 줄 곳은 IdP다, 그리로 가라"고 브라우저에게 알려주는 것뿐이다. 이 "알려주고 보내는" 동작이 리다이렉트다.

여기서 "보낸다"의 의미가 중요하다. 게이트웨이가 브라우저를 손으로 밀어 IdP로 옮기는 것이 아니다. 브라우저와 서버는 "요청 → 응답"만 주고받으므로, 게이트웨이가 브라우저를 이동시키는 유일한 방법은 브라우저의 요청에 대해 "여기 말고 저 주소로 다시 가라"는 답을 돌려주는 것이다. 그 답을 받은 브라우저가 스스로 그 주소로 다시 요청을 보내면, 결과적으로 브라우저가 IdP로 이동한 셈이 된다. HTTP에는 이 답을 표현하는 표준이 있는데, 상태 코드 302와 목적지를 담는 Location 헤더다. 

HTTP/1.1 302 Found
Location: https://login.example.com/authorize?client_id=...&redirect_uri=.../oauth/callback&...

Location에 담긴 주소가 IdP의 authorization_endpoint이고, 뒤의 쿼리 파라미터에 "누가(client_id) 보냈고, 로그인 끝나면 어디로(redirect_uri) 돌려보내라"가 적힌다. 브라우저는 이 302 응답을 받으면 Location의 주소로 자동으로 새 요청을 보내며, 이는 브라우저에 내장된 기본 동작이라 개발자가 따로 할 일은 없다. 그 결과 화면에 IdP 로그인 페이지가 뜬다. 아래 그림은 이 두 동작을 나눠 보여준다.

6~7. IdP 로그인과 콜백

개발자가 IdP에서 로그인하고 승인(consent, 게이트웨이가 자신의 이메일·그룹 정보에 접근하는 것을 개발자 본인이 허가하는 단계)하면(6), IdP는 브라우저를 게이트웨이의 /oauth/callback으로 되돌려보낸다(7). 이 "되돌려보낸다"는 5단계와 정확히 같은 302 리다이렉트이고, 방향만 반대다. IdP가 브라우저를 직접 옮기는 것이 아니라, Location 헤더에 게이트웨이의 콜백 주소를 담은 302 응답을 브라우저에 돌려주고, 브라우저가 스스로 그 주소로 이동한다(https://<gateway>/oauth/callback?code=...처럼 인증 코드가 쿼리에 실린다). 이 콜백 주소가 바로 public_url을 기준으로 만들어지는 redirect_uri이며, 5단계에서 게이트웨이가 IdP로 미리 알려준 값이자 IdP에 등록해 둔 값과 정확히 일치해야 한다.

redirect_uri를 왜 미리 등록하는가. IdP는 로그인이 끝나면 인증 코드를 redirect_uri로 돌려보낸다. 만약 IdP가 요청에 실려온 아무 주소로나 코드를 보낸다면, 공격자가 이 값을 자신의 서버로 바꿔 코드를 가로챌 수 있다. 그래서 IdP는 사전 등록된 값과 정확히 일치하는 주소에만 코드를 돌려보낸다. 이는 Claude Apps Gateway만의 요구가 아니라 OAuth 2.0의 표준 방어다. 게이트웨이를 ALB 뒤에 두면서 public_url을 내부 주소로 잘못 설정하면, IdP가 등록값과 다른 redirect_uri를 받아 콜백이 실패한다.

그런데 7단계에서 콜백으로 오는 값은 사용자 신원 정보가 아니라 인증 코드(authorization code)다. 이 코드는 "이 사용자가 방금 로그인을 마쳤다"를 증명하는 일회용 교환권일 뿐, 사용자가 누구인지는 담겨 있지 않다. 게이트웨이는 이 코드를 다시 IdP의 토큰 엔드포인트에 제시해(이때 PKCE로 검증) 진짜 정보를 받아오는데, 이 교환은 브라우저를 거치지 않고 게이트웨이와 IdP가 직접 주고받는다. 이렇게 받는 정보는 두 가지다. 하나는 사용자 신원을 담은 id_token으로, 게이트웨이는 이 토큰을 검증한 뒤 이메일·이메일 검증 여부·소속 그룹을 꺼낸다(그룹 정보로 모델 allowlist와 managed settings 정책을 정한다). 다른 하나는 리프레시 토큰으로, 이후 세션이 만료될 때 개발자를 다시 브라우저 로그인시키지 않고 조용히 갱신하는 데 쓴다.

PKCE: 코드를 가로채도 토큰으로 못 바꾸게 하는 장치. PKCE(Proof Key for Code Exchange)는 인증 코드 탈취를 무력화하는 OAuth 2.0 확장이다(RFC 7636). 한 쌍의 값을 쓰는데, code_verifier는 무작위 원본 비밀값이고 code_challenge는 그것을 SHA-256으로 해시한 값이다(해시라 되돌릴 수 없다). 이 플로우에서 OAuth 클라이언트 역할은 게이트웨이, 서버 역할은 IdP다.

① 발급(생성) — 로그인을 시작할 때 게이트웨이가 code_verifier를 만들고, 해시해 code_challenge를 만든다. ② 사용 — 게이트웨이가 authorization 요청에는 code_challenge(해시)만 실어 보내고, 나중에 코드를 토큰으로 교환할 때 원본 code_verifier를 제시한다. IdP가 이 원본을 해시해 앞서 받은 code_challenge와 일치하는지 검증하고, 일치해야만 토큰을 내준다. ③ 저장 — code_verifier(원본)는 게이트웨이가 로그인이 끝날 때까지만 임시 보관하고, code_challenge(해시)는 IdP가 인증 코드와 짝지어 보관한다. 브라우저에는 아무것도 저장되지 않는다.

그 결과 공격자가 브라우저 구간에서 인증 코드를 가로채도, 토큰 교환에 필요한 code_verifier는 게이트웨이만 갖고 있고 네트워크로 오간 적이 없어(오간 것은 되돌릴 수 없는 해시뿐) 코드만으로는 토큰을 받을 수 없다. (게이트웨이가 authorization-code 교환에 PKCE를 쓴다는 것은 공식 문서로 확인된 사실이고, verifier가 게이트웨이의 어느 저장소에 놓이는지 같은 구현 세부는 명시돼 있지 않다.)
왜 코드를 먼저 받고 다시 교환하는가. 사용자 신원 정보(id_token)를 처음부터 브라우저(URL)에 실어 보내면 브라우저 기록이나 로그에 남아 유출될 수 있다. 그래서 브라우저에는 의미 없는 일회용 코드만 실어 보내고, 실제 토큰은 게이트웨이가 IdP와 직접 교환한다. 여기에 PKCE까지 걸어, 코드가 중간에 탈취되더라도 검증값 없이는 토큰으로 바꿀 수 없게 한다. 게이트웨이와 IdP의 이 모든 통신은 표준 OpenID Connect(OIDC)의 authorization-code 플로우를 따른다(HTTPS 위에서 동작하며, SAML·LDAP은 지원하지 않는다).

8~10. 세션 확립

게이트웨이는 콜백으로 받은 인증 결과로 세션 토큰(JWT)을 발급하고 상태를 PostgreSQL에 기록한다(8). 그 다음 CLI의 polling 요청이 이 세션 토큰을 받아 대기를 끝낸다(9). 이제 로그인이 완료되어, 이후 CLI는 원본 IdP 자격증명 없이 이 세션 토큰만으로 게이트웨이와 통신한다(10). 여기까지가 최초 로그인 과정이며, 이후 세션 토큰이 만료됐을 때의 조용한 갱신·재로그인은 Lesson 3 5단계에서 다룬다.

왜 CLI와 브라우저를 분리하는가. 이렇게 나누면 CLI가 실행되는 기기와 브라우저가 실행되는 기기가 서로 달라도 된다. 예를 들어 SSH로 접속한 원격 서버에서 /login을 실행하고(CLI 구간), 확인 URL은 자신의 노트북 브라우저에서 여는(브라우저 구간) 구성이 가능하다. 웹 앱식 리다이렉트였다면 CLI가 실행되는 기기에 브라우저가 있어야 했을 것이다.
디바이스 인증은 "또 하나의 인증"이 아니라 조율 장치다. 디바이스 인증은 사용자가 누구인지 확인하는 보안 단계가 아니다. 실제 신원 확인은 전적으로 IdP 로그인이 담당한다. 그렇다면 두 단계를 두는 이유는 무엇인가. 일반 웹 앱은 접근하는 주체가 곧 브라우저라 그 브라우저를 바로 IdP로 리다이렉트하면 되지만, CLI에는 리다이렉트할 브라우저가 없다. 그래서 토큰을 받으려는 주체(CLI)와 실제로 로그인하는 주체(브라우저)를 분리해야 하고, 분리하고 나면 "브라우저에서 끝난 로그인 결과를 어느 CLI의 대기에 건네줄 것인가"라는 연결 문제가 생긴다. device_code(CLI가 자신을 식별)와 user_code(브라우저 로그인을 그 CLI 요청에 연결)가 바로 이 둘을 같은 로그인 시도로 묶는 역할을 한다. 즉 디바이스 인증은 인증을 한 번 더 하는 것이 아니라, 서로 다른 두 채널을 이어주는 조율 장치다.
다만 보안 기여가 전혀 없는 것은 아니다. 디바이스 확인 페이지는 same-origin POST만 허용하고 IP당 rate limit을 걸어(RFC 8628 §5.1), 짧은 user_code를 무차별 대입으로 알아맞히는 공격을 막는다. 하지만 이는 확인 코드가 추측당하지 않게 하는 부수적 방어일 뿐, 사용자 신원 확인 자체는 아니다.

브라우저에서 끝난 로그인 결과가 올바른 CLI의 대기(polling)로 전달되는 것은 무엇 덕분인가?

트러블슈팅 로그 — 로그인·추론까지 마주친 문제와 조치

실습 가이드를 따라 gateway를 배포한 뒤, 실제 로그인·추론에 성공하기까지 마주친 문제들을 겪은 순서대로 정리한다. 각 증상은 이전 문제를 고치고 나서야 드러난 다음 단계의 문제라, 순서 자체에 진단 흐름이 담겨 있다.

1 · 이미지를 재빌드·push해도 반영되지 않는다

gateway 이미지를 고쳐서 다시 빌드하고 같은 태그(test)로 push했는데, ECS Task를 재배포해도 예전 동작이 그대로였다. 원인은 ECS Task Definition이 이미지를 태그가 아니라 다이제스트(digest)로 고정하고 있었던 것이다. docker push로 같은 태그가 새 다이제스트를 가리키게 바뀌어도, Task Definition에 ...@sha256:... 형태로 박힌 참조는 그 옛 다이제스트를 계속 가리킨다. Task Definition의 이미지 필드를 ...claude-gateway:test(태그 참조)로 바꾼 새 revision을 등록하고서야 재빌드가 반영됐다.

2 · gateway hostname이 NXDOMAIN으로 resolve되지 않는다

gateway Task는 RUNNING인데 nslookup이 NXDOMAIN을 돌려줬다. 확인해 보니 gateway용 Cloud Map service 자체가 없었다 — postgres는 Service Discovery가 연결돼 postgres.claude-gw.local로 정상 등록됐지만, gateway ECS Service는 serviceRegistries가 빈 배열이라 Cloud Map에 전혀 등록되지 않은 상태였다. 여기에 더해 실습 도메인을 문서 예시(internal.example.com)로 바꾸기로 하면서, 이미 같은 VPC에 연결돼 있던 빈 internal.example.com zone을 지우고 그 이름으로 Cloud Map private DNS namespace를 새로 만들었다. gateway용 ECS Service(claude-gw-gateway)를 이 namespace의 Cloud Map service에 연결해 재생성하고서야 claude-gw.internal.example.com이 정상 resolve됐다.

같은 도메인의 zone을 두 개 만들지 않는다. 기존 zone과 같은 이름으로 Cloud Map namespace를 새로 만들면, 같은 VPC에 동일한 도메인을 가리키는 private hosted zone이 두 개 생겨 어느 쪽이 응답할지 보장되지 않는 split-brain 상태가 된다. 새 namespace를 만들기 전에 기존 zone을 먼저 정리해야 한다.

3 · VPN 연결·DNS는 되는데 게이트웨이 접속이 타임아웃난다

nslookup은 사설 IP를 정상적으로 돌려주는데, /login은 timeout of 10000ms exceeded로 실패했다. gateway ECS Service의 보안 그룹을 확인해 보니 postgres용 보안 그룹(인바운드가 TCP 5432 하나뿐)을 그대로 물고 있었다 — 새 gateway Service를 만들 때 실수로 재사용한 것이다. Client VPN에서 들어온 HTTPS(443) 트래픽이 보안 그룹 단계에서 조용히 드롭돼 타임아웃으로 나타났다. Client VPN 클라이언트 CIDR로부터의 443을 허용하는 전용 보안 그룹을 새로 만들어 물리자 타임아웃이 사라졌다.

4 · ECONNREFUSED <IP>:443

보안 그룹을 고치자 타임아웃 대신 즉시 거부로 바뀌었다 — 신호가 다르다는 것 자체가 힌트였다. 타임아웃은 트래픽이 조용히 드롭된다는 뜻이고, ECONNREFUSED는 SYN이 목적지까지 도달했지만 그 포트에 아무것도 리스닝하지 않아 즉시 RST가 온다는 뜻이다. gateway.yaml의 listen.port가 8080인데, 클라이언트는 https://<hostname>(포트 미지정 → 기본 443)로 접속을 시도했다. Fargate awsvpc 모드는 리버스 프록시 없이 컨테이너 포트가 곧 ENI 포트이므로, 443에는 리스너가 전혀 없었다. listen.port를 443으로 바꿔 이미지를 재빌드·재배포했다(Dockerfile에 USER 지정이 없어 root로 실행되므로 443 바인딩에 권한 문제는 없었다).

5 · TLS 인증서를 신뢰할 수 없다는 에러

Could not verify the gateway's TLS certificate ... self signed certificate 에러가 났다. 자체 서명 인증서라 OS 신뢰 저장소에 없는 게 당연한 결과다. ~/.claude/settings.json의 env.NODE_EXTRA_CA_CERTS에 인증서(tls/cert.pem, 개인키 아님) 경로를 지정해 해결했다. 이 파일을 만들 때 JSON 문법 오류(쉼표·닫는 중괄호 누락)로 한 번 더 헛돌았다 — 설정 파일을 고친 뒤에는 실제로 파싱되는지 python3 -c "import json; json.load(open(...))" 같은 방법으로 검증하는 게 안전하다.

6 · hostname이 인증서의 SAN과 일치하지 않는다

Hostname/IP does not match certificate's altnames: ... is not in the cert's altnames: DNS:<gateway-hostname>. 인증서의 SAN에 실제 hostname이 아니라 문서의 placeholder 문자열 <gateway-hostname>이 그대로 박혀 있었다 — openssl 명령의 -subj·-addext 값을 실제 hostname으로 바꾸지 않고 그대로 실행한 결과다. 인증서를 실제 hostname으로 재발급하고, 이미지를 재빌드·재배포하고, 클라이언트가 신뢰하는 인증서 파일도 새 것으로 교체했다.

7 · 디바이스 인증 코드를 입력한 뒤 반응이 없다

디바이스 인증 화면까지는 열렸지만, 코드를 제출한 뒤 아무 반응이 없었다. 게이트웨이 로그를 보면 device.verify가 result: "redirect"로 정상 응답하고 있었다 — 즉 게이트웨이는 Cognito 로그인 화면으로 리다이렉트를 지시했는데, 그 리다이렉트가 도달하지 못한 것이다. 원인은 Client VPN 엔드포인트가 풀 터널(SplitTunnel: False) 모드였던 것. 풀 터널은 인터넷 목적지로 가는 트래픽까지 전부 VPN으로 잡아채는데, Authorization rule과 route table에는 VPC CIDR만 허용·라우팅돼 있어 Cognito(퍼블릭 인터넷)로 가는 트래픽이 조용히 드롭됐다. Client VPN 설정 문서가 이미 "실습에서는 split-tunnel을 켜 두기를 권장한다"고 명시하고 있었는데, 그 옵션을 빠뜨린 것이 원인이었다. modify-client-vpn-endpoint --split-tunnel로 켜고 재연결하자 해결됐다.

8 · invalid_request: invalid_scope

split-tunnel을 켠 뒤로는 브라우저가 실제로 Cognito까지 도달했지만, 곧바로 invalid_scope 에러 페이지로 돌아왔다. 브라우저 개발자도구에서 /device/verify 응답의 Location 헤더를 확인해, 게이트웨이가 Cognito로 보내는 실제 authorize 요청의 scope 값을 봤다 — openid profile email offline_access. Cognito는 offline_access를 지원하지 않는다(Cognito가 허용하는 scope는 openid·email·phone·profile·aws.cognito.signin.user.admin뿐이고, refresh token은 이 scope 없이도 authorization code grant에서 자동 발급된다). 게이트웨이 공식 문서의 트러블슈팅 표에 정확히 이 케이스가 있었다: oidc.scopes를 IdP가 받아들이는 목록으로 override하라는 것. 

oidc:
  scopes: [openid, profile, email]   # offline_access 제외 — Cognito 미지원
session:
  ttl_hours: 8    # refresh token이 없으니 세션을 늘려 재로그인 빈도를 줄인다

여기에 두 가지가 더 겹쳤다. 첫 시도에서는 oidc.scopes 줄을 실제로는 빼먹고 allowed_email_domains를 중복으로 적어 넣는 복붙 실수가 있었고(YAML이 마지막 값을 취해 도메인은 우연히 맞았지만 scope는 그대로 기본값이었다), Cognito App Client의 AllowedOAuthScopes에도 애초에 profile이 빠져 있어 별도로 추가해야 했다.

9 · Cognito 테스트 사용자가 FORCE_CHANGE_PASSWORD 상태

scope 문제를 고친 뒤 마주친 다음 관문이다. 테스트 사용자를 만든 뒤 임시 비밀번호를 정식 비밀번호로 바꾸는 절차를 거치지 않은 상태였다. admin-set-user-password에 --permanent를 줘서 임시 비밀번호 절차를 건너뛰고 바로 CONFIRMED 상태로 만들었다.

10 · Invalid request. Please check your input and try again.

Cognito Hosted UI가 보여주는 일반적인 에러 페이지였다. App Client 설정을 전부 훑어보니 SupportedIdentityProviders가 비어 있었다 — Hosted UI 로그인은 이 필드에 COGNITO(User Pool 자체 로그인)가 포함돼야 동작한다. update-user-pool-client에 --supported-identity-providers COGNITO를 추가하자 해결됐다.

11 · 로그인은 되는데 추론에서 403 upstream denied the request

로그인·리다이렉트·콜백까지 전부 성공한 뒤, 실제 모델 호출에서 막혔다. Task Role의 인라인 정책은 bedrock:InvokeModel을 foundation-model/*에만 허용하고 있었는데, 직접 invoke-model을 테스트해 보니 최신 Claude 모델은 on-demand 직접 호출이 막혀 있고 cross-region inference profile을 거쳐야 했다(ValidationException: ... isn't supported. Retry ... with the ID or ARN of an inference profile). inference profile은 foundation-model과는 별도의 리소스 타입(inference-profile/*)이라, 기존 정책의 리소스 범위에 들지 않아 bedrock:InvokeModel 자체가 implicitDeny였다(iam simulate-principal-policy로 확인). 정책을 아래로 넓혀 해결했다. 

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
      "Resource": [
        "arn:aws:bedrock:us-east-1::foundation-model/*",
        "arn:aws:bedrock:us-east-2::foundation-model/*",
        "arn:aws:bedrock:us-west-2::foundation-model/*",
        "arn:aws:bedrock:*:<account-id>:inference-profile/*"
      ]
    }
  ]
}

cross-region inference profile(us. 접두사)은 내부적으로 여러 리전의 foundation model로 라우팅되므로, inference-profile 리소스 권한과 함께 그 리전들의 foundation-model 권한도 함께 필요하다.

11개 문제 중 다수가 같은 값을 두 곳(이미지에 굽는 설정, ECS/Cognito/IAM 리소스, 클라이언트 설정)에 따로 넣어야 하는 구조에서 비롯됐다 — hostname은 인증서·gateway.yaml·Cognito 콜백 URL 세 곳에, scope는 gateway.yaml과 Cognito App Client 양쪽에 일치해야 했다. 에러 신호의 종류(타임아웃 vs 즉시 거부, 로그의 redirect 유무, 실제 요청 URL의 파라미터)를 구분해 어느 계층에서 막혔는지 좁혀가는 것이 매번 유효했다.

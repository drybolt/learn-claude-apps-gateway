Route53 Private Hosted Zone 설정 — 게이트웨이 hostname을 VPC 안에서 resolve

단계 0에서 이름만 정해 둔 게이트웨이 hostname을, VPC 안에서만 유효한 사설 DNS 이름으로 만든다. 인터넷 DNS와 분리되므로 도메인을 실제로 소유하지 않아도 된다.

실습 가이드의 단계 2 · 네트워크(단일 AZ)에서 참조하는 문서다. 게이트웨이는 Private Subnet의 사설 IP로만 접근을 허용하므로, 랩탑의 CLI·브라우저가 게이트웨이에 닿으려면 그 hostname이 사설 IP로 resolve돼야 한다. private hosted zone은 이 이름→사설 IP 매핑을 VPC 내부에서만 담당하는 DNS 영역이다. 이 문서는 VPC DNS 속성 확인 → private hosted zone 생성 → (나중에) A 레코드 채우기를 순서대로 다룬다.

이 가이드는 부모 도메인으로 zone을 만드는 관례 방식을 쓴다. zone 도메인 이름은 게이트웨이 hostname의 부모 도메인(internal.example.com)으로 만들고, 그 zone 안에 이름이 claude-gw인 레코드를 두어 완성 이름이 claude-gw.internal.example.com이 되게 한다. hosted zone은 "자기 도메인 이름과 그 하위(subdomain)에 대한 레코드를 담는 그릇"이므로, 부모 도메인으로 zone을 만들면 claude-gw, db, api 같은 형제 이름을 같은 층위에 나란히 추가할 수 있다. 게이트웨이 외에 이름 있는 리소스를 더 두거나 운영 환경으로 확장할 때 이 방식이 자연스럽다.
지금은 zone만 준비하고, A 레코드는 단계 5에서 채운다. 게이트웨이 hostname의 A 레코드는 gateway Task(ECS)의 사설 IP가 정해져야 채울 수 있는데, 그 IP는 실습 가이드 단계 5에서 나온다. 그래서 단계 2에서는 빈 zone을 만들어 VPC에 연결하는 데까지만 하고, 레코드 값은 이후에 채운다. 이 문서의 4절은 그 나중 작업을 미리 정리해 둔 것이다.

1 · 사전 조건 — VPC DNS 속성 두 개

private hosted zone은 VPC의 두 DNS 속성이 모두 true여야 동작한다. 하나라도 꺼져 있으면 zone을 만들어도 이름이 resolve되지 않는다.

  • enableDnsSupport — VPC 안에서 Amazon DNS 서버(VPC Route53 Resolver, VPC CIDR + 2 = 10.0.0.2)로의 DNS 질의가 동작하게 한다. private hosted zone의 레코드는 이 Resolver를 통해 응답된다.
  • enableDnsHostnames — VPC의 인스턴스가 DNS hostname을 받도록 한다. AWS 공식 안내상 DNS support가 켜져 있어야만 DNS hostnames를 켤 수 있다(순서 주의).

현재 값 확인:

VPC_ID="vpc-xxxxxxxx"   # 단계 2에서 만든 VPC의 ID

aws ec2 describe-vpc-attribute --vpc-id ${VPC_ID} --attribute enableDnsSupport
aws ec2 describe-vpc-attribute --vpc-id ${VPC_ID} --attribute enableDnsHostnames
# → 각각 "Value": true 여야 정상

false이면 다음으로 켠다(DNS support를 먼저 켠다):

aws ec2 modify-vpc-attribute --vpc-id ${VPC_ID} --enable-dns-support   "{\"Value\":true}"
aws ec2 modify-vpc-attribute --vpc-id ${VPC_ID} --enable-dns-hostnames "{\"Value\":true}"
# 성공하면 출력이 없다

2 · Private Hosted Zone 생성 (콘솔)

  1. Route53 콘솔(console.aws.amazon.com/route53)에서 왼쪽 Hosted zones → Create hosted zone.
  2. Domain name — 게이트웨이 hostname의 부모 도메인을 입력한다(예: internal.example.com). 단계 0의 hostname이 claude-gw.internal.example.com이면, 그 앞의 claude-gw를 뺀 나머지가 부모 도메인이다.
  3. Type — Private hosted zone을 선택한다.
  4. VPCs to associate with the hosted zone — Region은 us-east-1, VPC는 단계 2에서 만든 VPC를 선택한다.
  5. Create hosted zone을 눌러 생성한다. 이 시점에는 (Route53이 자동 생성하는 NS·SOA 레코드 외에) 게이트웨이용 레코드가 없는 빈 zone이다.
zone 이름과 hostname의 관계 (헷갈리기 쉬운 지점). zone 도메인 이름(internal.example.com)은 게이트웨이 hostname 전체(claude-gw.internal.example.com)와 다르다. hostname은 이 zone 안의 claude-gw 레코드로 표현되며, "레코드 이름(claude-gw) + zone 이름(internal.example.com)"이 합쳐져 완성 이름이 된다. 즉 단계 0의 hostname을 그대로 zone 이름에 넣지 않는다 — 부모 도메인만 넣고, hostname은 4절에서 claude-gw 레코드로 채운다.

참고 — CLI로 만들 경우

콘솔 대신 CLI로 만들 수도 있다. private zone은 --vpc에 VPCId·VPCRegion이 필수이고, 생성 시에는 VPC 하나만 연결할 수 있다(추가 연결은 이후 associate-vpc-with-hosted-zone으로). --caller-reference는 중복 요청을 구분하는 임의의 고유 문자열이다. 

aws route53 create-hosted-zone \
  --name internal.example.com \
  --caller-reference "$(date +%s)" \
  --vpc VPCRegion=us-east-1,VPCId=${VPC_ID} \
  --hosted-zone-config PrivateZone=true,Comment="claude gateway private zone"

3 · 연결 확인

zone이 해당 VPC에 연결됐는지 확인한다. 이 목록에 단계 2의 VPC가 나오면 정상이다. 

aws route53 list-hosted-zones-by-vpc --vpc-id ${VPC_ID} --vpc-region us-east-1

4 · A 레코드 채우기 (단계 5에서 수행)

gateway Task의 사설 IP가 정해진 뒤(실습 가이드 단계 5), 이 zone 안에 이름이 claude-gw인 A 레코드를 만들어 hostname → 사설 IP를 가리키게 한다. 콘솔 절차:

  1. Route53 → Hosted zones에서 2절에서 만든 private hosted zone(internal.example.com)을 선택하고 Create record.
  2. Quick create가 보이면 Switch to wizard로 전환하고, Routing policy = Simple routing을 선택한 뒤 Next.
  3. Define simple record에서:
    • Record name — claude-gw를 입력한다(뒤의 .internal.example.com은 zone 이름이라 콘솔에 이미 붙어 있다). 완성 이름은 claude-gw.internal.example.com이 된다.
    • Record type — A.
    • Value — gateway Task의 사설 IP(예: 10.0.1.x).
    • TTL — 짧게(예: 60초) 둔다. 재배포로 IP가 바뀔 때 반영이 빠르다.
  4. Define simple record → Create records로 저장한다.

CLI로는 change-resource-record-sets의 UPSERT로 같은 작업을 한다. Name에는 완성 이름(FQDN)을 넣는다:

aws route53 change-resource-record-sets \
  --hosted-zone-id <ZONE_ID> \
  --change-batch '{
    "Changes": [{
      "Action": "UPSERT",
      "ResourceRecordSet": {
        "Name": "claude-gw.internal.example.com",
        "Type": "A",
        "TTL": 60,
        "ResourceRecords": [{ "Value": "10.0.1.x" }]
      }
    }]
  }'
같은 zone에 리소스를 더 추가할 때. 이 zone은 부모 도메인이므로, 게이트웨이 외에 이름 있는 리소스를 더 두려면 같은 절차로 레코드만 추가하면 된다 — 예를 들어 Record name에 db를 넣으면 db.internal.example.com이, api를 넣으면 api.internal.example.com이 된다. 모두 claude-gw와 같은 층위의 형제 이름으로, zone을 새로 만들 필요가 없다.
여기서 채운 IP는 재배포 때 바뀐다 — 자동 갱신은 Service Discovery로. Fargate Task에는 고정 IP를 붙일 수 없어, Task가 재생성되면 사설 IP가 바뀐다. 그러면 이 절에서 손으로 채운 A 레코드는 낡은 IP를 가리키게 되어, 재배포 때마다 다시 채워야 한다. 이 갱신을 ECS가 자동으로 하게 하려면 ECS Service Discovery (AWS Cloud Map)를 쓴다 — 이름이 항상 현재 Task의 IP를 따라가는 원리와 설정 절차를 그 문서에서 다룬다.

5 · resolve 확인

Client VPN으로 랩탑을 VPC에 넣은 상태(단계 3)에서, hostname이 사설 IP로 풀리는지 확인한다. VPN이 연결돼 있고 엔드포인트 DNS가 VPC Route53 Resolver(10.0.0.2)로 지정돼 있어야 한다. 

nslookup claude-gw.internal.example.com
# → 4절에서 넣은 사설 IP(10.0.x.x)가 나와야 정상
막히면 여기부터.
  • 이름이 아예 안 풀림 → 1절의 VPC DNS 속성(enableDnsSupport·enableDnsHostnames)이 둘 다 true인지, zone이 3절대로 해당 VPC에 연결됐는지 확인한다.
  • VPN 연결 중인데 안 풀림 → Client VPN 설정에서 엔드포인트 DNS가 10.0.0.2로 지정됐는지 확인한다(가장 자주 누락되는 항목).
  • NXDOMAIN이 뜸 → zone은 매칭되는데 레코드가 없을 때 Resolver는 NXDOMAIN을 반환한다. 4절의 claude-gw 레코드가 이 zone에 실제로 있는지, Record name이 claude-gw(부모 도메인을 뺀 부분)로 정확한지 확인한다. 네임스페이스가 겹치는 다른 private zone이 있으면 가장 구체적인 zone이 우선하므로, 의도치 않은 겹침이 없는지도 본다.

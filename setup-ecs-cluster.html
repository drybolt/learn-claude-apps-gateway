ECS 설정 — 클러스터 · postgres Task · gateway Task (Fargate)

최신 ECS 콘솔(console v2)로 Fargate 클러스터를 만들고, postgres와 gateway를 별도 Service로 띄운다.

실습 가이드 단계 5에서 참조하는 문서다. 단계 5는 "gateway와 postgres를 별도 Task로 분리한다"는 설계 의도만 담고 있으므로, 여기서 클러스터 생성부터 두 Service 배포까지의 콘솔 절차를 순서대로 다룬다. postgres를 먼저 띄워 Cloud Map 이름을 등록한 뒤 gateway를 나중에 띄우는 순서를 지킨다 — gateway는 시작 시점에 postgres.claude-gw.local로 DB를 찾기 때문이다.

선행 조건. 이 문서를 시작하기 전에 다음이 준비돼 있어야 한다. 이미지 준비에서 gateway 이미지를 ECR에 push했고(postgres는 공개 postgres:16 이미지를 그대로 쓴다), 단계 2에서 VPC·Private Subnet(10.0.1.0/24)·NAT Gateway를 만들었으며, 단계 0에서 hostname과 CIDR을 확정했다. gateway에 넘길 비밀값(OIDC_CLIENT_SECRET·GATEWAY_JWT_SECRET·GATEWAY_POSTGRES_URL)도 확보해 두어야 한다.

1 · 클러스터 생성

클러스터는 Task·Service가 실행되는 논리적 단위다. Fargate는 서버리스라 EC2 인스턴스를 직접 관리하지 않는다.

  1. ECS 콘솔(console.aws.amazon.com/ecs/v2, us-east-1)에서 좌측 Clusters → Create cluster.
  2. Cluster name = claude-gw-cluster.
  3. Infrastructure = AWS Fargate (serverless)를 선택한다. (콘솔이 Fargate·Fargate Spot capacity provider를 자동으로 연결한다.)
  4. 나머지는 기본값으로 두고 Create. 콘솔이 CloudFormation 스택으로 필요한 리소스를 만든다.
클러스터 네임스페이스는 지금 지정하지 않는다. 클러스터 생성 화면에도 네임스페이스(Service Connect용) 옵션이 있지만, 이 실습은 Service Discovery(Cloud Map DNS) 방식을 쓰므로 여기서 만들지 않는다. Cloud Map 네임스페이스(claude-gw.local)는 3단계에서 postgres Service를 만들 때 함께 생성된다. 두 방식의 차이는 Service Discovery 설정 문서에서 다룬다.

2 · postgres Task Definition 작성

Task Definition은 "이 컨테이너를 어떤 이미지·CPU·메모리·환경변수로 실행하라"는 설계도다. 먼저 postgres용을 만든다.

  1. 좌측 Task definitions → Create new task definition.
  2. Task definition family = claude-gw-postgres.
  3. Infrastructure requirements
    • Launch type = AWS Fargate.
    • Task size = 예: CPU 0.5 vCPU, Memory 1 GB. (테스트 규모. Fargate는 CPU·메모리 조합이 정해져 있으므로 허용되는 값에서 고른다.)
    • Task role은 비워도 된다(postgres는 다른 AWS API를 호출하지 않는다). Task execution role은 CloudWatch 로그 전송을 위해 ecsTaskExecutionRole을 선택한다(없으면 콘솔이 생성 제안). postgres는 Docker Hub 공개 이미지를 쓰므로 이미지 pull 자체에는 이 role이 필요 없다 — ECR private repo pull에만 이 role의 권한이 쓰인다.
  4. Container - 1
    • Name = postgres.
    • Image URI = postgres:16 (Docker Hub 공개 이미지).
    • Port mappings = 컨테이너 포트 5432, 프로토콜 TCP.
    • Environment variables에 초기화 값을 추가한다. 예:
      KeyValue
      POSTGRES_USERgateway
      POSTGRES_PASSWORD임의의 비밀번호(예: changeme123 — 테스트값이므로 실제 배포 전 반드시 교체)
      POSTGRES_DBgateway
      이 값들이 단계 4 GATEWAY_POSTGRES_URL의 사용자·비밀번호·DB 이름과 일치해야 한다.
  5. Create.

3 · postgres Service 생성 (Cloud Map 이름 등록)

Service는 Task를 지정한 개수만큼 띄우고 유지한다. 이 단계에서 Service Discovery를 켜면 ECS가 Cloud Map private DNS namespace를 자동으로 만들고 이 Task를 postgres.claude-gw.local로 등록한다.

  1. Clusters → claude-gw-cluster → Services 탭 → Create.
  2. Compute options = Launch type = Fargate.
  3. Service details
    • Task definition = claude-gw-postgres, Revision = 최신.
    • Service name = postgres.
    • Desired tasks = 1.
  4. Networking
    • VPC = 단계 2에서 만든 VPC.
    • Subnets = Private Subnet(10.0.1.0/24)만 선택한다.
    • Security group = 새로 만든다. 이름 = claude-gw-postgres-sg. Inbound rules는 다음과 같이 추가한다(gateway SG를 아직 안 만들었으면, gateway Service 생성 후 이 규칙을 추가한다).
      TypeProtocolPort rangeSource
      Custom TCPTCP5432Custom → claude-gw-gateway-sg(보안 그룹 ID로 검색해 선택)
      Source를 CIDR이 아니라 보안 그룹으로 지정하면, gateway Task가 재배포로 IP가 바뀌어도 규칙을 다시 손댈 필요가 없다.
    • Public IP = Disabled (Private Subnet이므로 공인 IP를 붙이지 않는다).
  5. Service discovery 섹션을 펼쳐 Use service discovery를 켠다.
    • Configure namespace = Create a new namespace, 네임스페이스 이름 = claude-gw.local.
    • Service discovery name = postgres. (완성 이름이 postgres.claude-gw.local이 된다 — 단계 4 postgres_url과 일치.)
    • DNS record type = A. (Task가 awsvpc 네트워크 모드이므로 A 레코드를 쓴다. Task의 사설 IP가 이 이름으로 등록된다.)
  6. Create. Task가 RUNNING이 되면 Cloud Map에 IP가 등록된다.
Service Discovery를 켜면 Route53 private hosted zone이 하나 더 생긴다. 이 claude-gw.local zone은 Cloud Map이 관리하는 것으로, 단계 2에서 직접 만든 internal.example.com(게이트웨이 hostname용) zone과는 별개다. 둘은 용도가 다르다 — 하나는 서비스 간 내부 이름(postgres.claude-gw.local), 다른 하나는 랩탑이 접속하는 게이트웨이 이름(claude-gw.internal.example.com)이다.

4 · gateway Task Definition 작성 (비밀값 환경변수 주입)

gateway 이미지에는 gateway.yaml과 TLS 인증서가 이미 포함돼 있고, gateway.yaml은 비밀값을 ${ENV_VAR} 참조로만 담고 있다. 실제 값은 여기 Task Definition의 환경변수로 런타임에 주입한다.

  1. Task definitions → Create new task definition.
  2. Task definition family = claude-gw-gateway.
  3. Infrastructure requirements
    • Launch type = AWS Fargate. Task size = 예: CPU 1 vCPU, Memory 2 GB.
    • Task role = gateway가 Bedrock을 호출하므로, bedrock:InvokeModel·bedrock:InvokeModelWithResponseStream을 가진 역할을 지정한다(단계 5 항목 3, 아래 callout 참고). Task execution role = ecsTaskExecutionRole.
  4. Container - 1
    • Name = gateway.
    • Image URI = ECR에 push한 이미지 URI를 태그로 지정한다(<account-id>.dkr.ecr.us-east-1.amazonaws.com/claude-gateway:test). 다이제스트(@sha256:...)로 지정하면 이후 같은 태그로 재빌드·push해도 ECS가 그 옛 다이제스트만 계속 pull해, 재배포가 반영되지 않는다.
    • Port mappings = 컨테이너 포트 443(gateway.yaml의 listen.port — 8080이 아니다, ALB 없이 게이트웨이가 직접 443을 종단하므로), TCP.
    • Environment variables — 아래 값을 각각 Key/Value로 추가한다. Value type = Value로 두고 값을 직접 입력한다.
      KeyValue
      OIDC_CLIENT_SECRETCognito App Client의 secret
      GATEWAY_JWT_SECRET세션 JWT 서명 키. openssl rand -base64 32로 생성한 값을 그대로 쓴다(최소 32바이트의 암호학적 난수 — 예측 가능한 값을 쓰면 세션 토큰이 위조될 수 있다). 예: DLauvO0WLBxiRyPhiyHbi6ni2GyZHUbAFHD77S/L/Gg= (예시일 뿐이므로 그대로 쓰지 말고 배포마다 새로 생성한다)
      GATEWAY_POSTGRES_URLpostgres://gateway:changeme123@postgres.claude-gw.local:5432/gateway (2단계 POSTGRES_USER·POSTGRES_PASSWORD·POSTGRES_DB와 일치)
  5. Create.
Task Role의 Bedrock 권한은 inference-profile 리소스까지 포함해야 한다. 최신 Claude 모델(예: Sonnet 4.5 이후)은 Bedrock에서 on-demand 직접 호출이 막혀 있고, cross-region inference profile을 거쳐야 한다(ValidationException: ... Retry your request with the ID or ARN of an inference profile). inference profile은 foundation-model과는 별도의 리소스 타입이라, Resource를 foundation-model/*로만 좁혀 두면 bedrock:InvokeModel 자체가 implicitDeny로 막혀 403 upstream denied the request가 난다. Task Role의 인라인 정책을 아래처럼 넓힌다(cross-region inference profile은 여러 리전의 foundation model로 라우팅되므로 그 리전들의 foundation-model 권한도 함께 필요하다). 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["bedrock:InvokeModel", "bedrock:InvokeModelWithResponseStream"],
      "Resource": [
        "arn:aws:bedrock:us-east-1::foundation-model/*",
        "arn:aws:bedrock:us-east-2::foundation-model/*",
        "arn:aws:bedrock:us-west-2::foundation-model/*",
        "arn:aws:bedrock:*:<account-id>:inference-profile/*"
      ]
    }
  ]
}
이 방식은 secret이 Task Definition에 평문으로 남는다 — 테스트 한정이다. Value type = Value로 넣은 값은 describe-task-definition이나 콘솔에서 그대로 조회된다. 운영에서는 값을 Secrets Manager에 저장하고, 환경변수 대신 Value type = ValueFrom(콘솔의 "Add environment variable from" / Task Definition JSON의 secrets)으로 그 ARN을 참조한다. 이때 Task execution role에 secretsmanager:GetSecretValue 권한이 필요하고, ECS가 컨테이너 시작 시점에 값을 읽어 환경변수로 주입한다.

5 · gateway Service 생성

postgres와 같은 방식으로 gateway Service를 만든다. gateway는 내부에 이름을 노출할 필요가 없지만(랩탑은 Route53 private zone의 A 레코드로 접근한다), 같은 클러스터·같은 VPC에 두어 postgres.claude-gw.local을 resolve할 수 있게 한다.

  1. claude-gw-cluster → Services → Create.
  2. Launch type = Fargate.
  3. Task definition = claude-gw-gateway, Service name = gateway, Desired tasks = 1.
  4. Networking
    • VPC = 같은 VPC, Subnets = Private Subnet.
    • Security group = 3단계의 claude-gw-postgres-sg를 실수로 재선택하지 않는다 — 콘솔이 최근 만든 보안 그룹을 목록 위쪽에 보여줘 혼동하기 쉽다. gateway용으로 새로 만든다. 이름 = claude-gw-gateway-sg. Inbound rules는 다음과 같이 추가한다(랩탑이 게이트웨이에 HTTPS로 접근).
      TypeProtocolPort rangeSource
      HTTPSTCP443Custom → 172.16.0.0/22(단계 0의 Client VPN 클라이언트 CIDR)
    • Public IP = Disabled.
  5. Service discovery는 켜지 않아도 된다(gateway는 내부 이름으로 불릴 필요가 없다).
  6. Create.
보안 그룹 규칙은 양쪽을 맞춰 정리한다. claude-gw-gateway-sg가 만들어졌으면, 3단계 claude-gw-postgres-sg의 인바운드에 claude-gw-gateway-sg로부터의 5432 허용 규칙을 추가한다. 정리하면 — claude-gw-postgres-sg: claude-gw-gateway-sg → 5432 허용, claude-gw-gateway-sg: Client VPN CIDR → 443 허용. gateway가 Cognito·Bedrock·ECR로 나가는 아웃바운드는 NAT Gateway 경로를 쓴다(단계 2).

6 · A 레코드 연결 (hostname → gateway 사설 IP)

gateway Task가 RUNNING이 되면 사설 IP가 정해진다. 이 IP를 단계 2에서 만든 Route53 private hosted zone(internal.example.com)의 A 레코드(이름 = claude-gw)에 채운다. 이것으로 단계 0에서 이름만 정해 둔 claude-gw.internal.example.com이 실제 IP와 연결되고, VPN으로 들어온 랩탑이 이 이름을 사설 IP로 resolve한다. 자세한 절차는 Route53 Private Zone 설정 문서에 있다.

gateway Task IP는 재배포 때 바뀐다. Fargate Task는 재배포·교체 시 사설 IP가 달라지므로, gateway를 재배포하면 이 A 레코드를 다시 채워야 한다. 매번 갱신이 번거로우면 gateway도 Service Discovery(gateway.claude-gw.local)로 등록하거나, 정석 구성에서는 ALB를 앞에 두어 고정 진입점을 만든다.

7 · 실행 확인

  1. 클러스터의 Tasks 탭에서 postgres·gateway Task가 모두 RUNNING인지 본다.
  2. gateway Task의 Logs 탭(CloudWatch)에서 기동 로그를 확인한다 — ${OIDC_CLIENT_SECRET} 등이 값으로 치환돼 설정이 로드됐는지, DB 연결이 성공했는지 본다.
  3. DB 연결 오류가 나면 postgres.claude-gw.local resolve 여부부터 확인한다(Service Discovery 설정 5절의 resolve 확인 방법).
막히면 여기부터.
  • gateway가 DB에 못 붙음 → postgres Task가 RUNNING인지, Cloud Map에 postgres.claude-gw.local이 등록됐는지, claude-gw-postgres-sg가 claude-gw-gateway-sg로부터의 5432를 허용하는지 확인한다.
  • gateway가 시작하다 secret 오류 → gateway Task Definition의 환경변수 3개(OIDC_CLIENT_SECRET·GATEWAY_JWT_SECRET·GATEWAY_POSTGRES_URL)가 모두 있는지, 값이 정확한지 확인한다.
  • gateway Task가 PROVISIONING에서 멈추거나 이미지 pull 실패로 STOPPED됨 → gateway는 ECR에서 이미지를 pull하는데, ECR도 VPC 엔드포인트가 없으면 NAT Gateway를 거쳐야 접근된다. Private Subnet의 라우팅이 NAT Gateway를 향하는지 확인한다(단계 2).
  • gateway가 뜬 뒤 Cognito·Bedrock 호출에서 실패 → 마찬가지로 NAT Gateway 라우팅을 확인한다. Cognito·Bedrock 모두 VPC 엔드포인트를 제공하지 않아 이 아웃바운드도 NAT를 거친다.
  • 랩탑에서 게이트웨이에 접속 불가 → claude-gw-gateway-sg가 postgres SG를 잘못 재사용하고 있지 않은지, 실제로 Client VPN CIDR로부터의 443을 허용하는지, A 레코드가 현재 Task IP와 맞는지 확인한다. 보안 그룹이 맞는데 ECONNREFUSED가 나면 gateway.yaml의 listen.port와 위 Port mappings가 443으로 일치하는지 확인한다.
  • 로그인은 되는데 모델 호출에서 403 upstream denied the request → 위 Task Role callout대로 IAM 정책에 inference-profile 리소스가 포함돼 있는지, Bedrock 모델 액세스가 활성화됐는지 확인한다.

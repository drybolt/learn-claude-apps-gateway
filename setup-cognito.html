Cognito 설정 — User Pool · App Client · 테스트 사용자

게이트웨이가 로그인을 위임할 OIDC IdP를 최신 Cognito 콘솔로 준비한다.

실습 가이드의 단계 1에서 참조하는 문서다. Claude Apps Gateway는 로그인 전체를 IdP에 위임하므로(SAML·LDAP 미지원, OIDC 전용), IdP 없이는 어떤 테스트도 시작할 수 없다. 이 문서는 애플리케이션 생성 → 생성 후 설정 → 테스트 사용자 → 값 메모를 순서대로 다룬다.

최신 콘솔은 "애플리케이션 중심" 흐름이라 User Pool 이름을 먼저 입력하지 않는다. 예전 콘솔은 User Pool을 먼저 이름 붙여 만들었지만, 최신 콘솔은 애플리케이션 정보만 입력하면 User Pool과 App Client가 함께 자동 생성된다. 그래서 시작 화면에 풀 이름 입력란이 없는 것이 정상이다. 풀 이름은 생성 후 개요(overview) 화면에서 바꾼다.

1 · 애플리케이션 생성 (User Pool·App Client 자동 생성)

Cognito 콘솔(us-east-1)의 User pools 메뉴에서 Create user pool을 눌러 시작한다. 이 시작 화면에서 입력하는 값은 다음이 전부이며, "Create your application"을 누르면 Cognito가 User Pool과 App Client를 기본 설정으로 함께 만든다.

  1. Define your application — Application type으로 Traditional web application을 고른다.
  2. Name your application — 애플리케이션(App Client) 이름을 입력한다. 예: claude-gw-app.
  3. Configure options
    • Options for sign-in identifiers = Email
    • Required attributes for sign-up = email
  4. Add a return URL — https://<gateway-hostname>/oauth/callback(단계 0의 hostname). 이 값이 App Client의 콜백 URL이 된다.
  5. Create your application을 누른다.
왜 Traditional web application인가. 게이트웨이는 client_secret을 쓰는 confidential 클라이언트다. client secret은 서버가 안전하게 보관할 수 있을 때만 의미가 있는데, Cognito의 애플리케이션 유형 중 secret을 기본 포함하는 것이 Traditional web application(서버 사이드 웹앱)이다. Single-page application·Mobile app은 브라우저·기기에서 도는 public 클라이언트라 secret을 쓰지 않으므로 게이트웨이 설정과 맞지 않는다. 공식 문서 기준으로, 나중에 secret 유무를 바꾸려면 새 App Client를 Traditional web application 또는 Machine-to-machine 유형으로 다시 만들어야 한다.
생성 후 되돌릴 수 없는 선택이 있다. 사인인 식별자(Email)와 필수 속성은 User Pool 생성 후 변경할 수 없다. 바꾸려면 새 User Pool을 만들어 사용자를 이전해야 하므로, "Configure options" 단계에서 정확히 정한다.

2 · 생성 후 설정 (개요 화면)

애플리케이션이 만들어지면 User Pool 개요 화면에서 다음을 마저 설정한다. 여기서부터는 생성 후에도 바꿀 수 있는 값이다.

  1. User Pool 이름 변경(선택) — 자동 생성된 기본 이름을 claude-gw-pool 등으로 바꾼다. 실습 식별을 쉽게 하기 위한 것이며 동작에는 영향이 없다.
  2. 이메일 자동 검증 활성화 — 가입 시 이메일을 검증하게 해 사용자의 email_verified가 true가 되도록 한다. 게이트웨이는 이 값이 true가 아닌 사용자를 거부한다.
  3. MFA = No MFA — 테스트 구성이므로 다단계 인증은 끈다. (운영 전환 시 켜는 것을 검토한다.)
  4. 로그인 페이지 도메인 생성 — 좌측 Branding 메뉴의 Domain에서, Actions → Create Cognito domain을 눌러 Cognito 도메인 방식으로 만든다. 도메인 접두어를 입력하면 로그인 페이지 주소가 정해진다. 예: 접두어 claude-gw-auth → https://claude-gw-auth.auth.us-east-1.amazoncognito.com. 사용자가 실제로 아이디·비밀번호를 입력하는 OIDC 로그인 페이지가 이 도메인에서 열린다. 접두어는 리전 안에서 유일해야 하므로 이미 쓰이는 이름이면 다른 이름을 쓴다. 도메인을 만들 때 Branding version을 선택하는데, Managed login(새 브랜딩 편집기)과 Hosted UI (classic) 중 하나다. 게이트웨이 연동은 어느 쪽이든 OIDC 로그인 페이지로 동일하게 작동하므로, 테스트에서는 요금제 제약이 없는 Hosted UI (classic)를 선택하면 된다. (Managed login은 Lite가 아닌 feature plan(Essentials 또는 Plus, 유료)에서만 쓸 수 있어 Lite 사용 시 콘솔이 요금제 업그레이드를 요구한다.)
  5. App Client 확인 — Traditional web application이면 client secret이 이미 생성돼 있다. App Client 상세에서 콜백 URL이 https://<gateway-hostname>/oauth/callback인지도 확인한다.
  6. App Client의 Hosted UI 설정을 확인한다 — App Client 상세 → Login pages configuration → Edit에서 아래 두 가지를 반드시 확인한다. 둘 중 하나라도 빠지면 로그인 화면 진입 전에 에러가 난다.
    • Identity providers에 Cognito user pool이 체크돼 있어야 한다. 이게 비어 있으면(SupportedIdentityProviders가 빈 상태) Hosted UI가 Invalid request. Please check your input and try again.라는 일반 에러만 보여주고 로그인 폼 자체를 띄우지 않는다.
    • OAuth 2.0 grant types = Authorization code grant, OpenID Connect scopes에 OpenID·Email·Profile을 체크한다. Profile을 빠뜨리면 게이트웨이가 표준 OIDC 클라이언트로서 요청하는 scope와 어긋나 invalid_scope로 거부된다. offline_access에 대응하는 항목은 켜지 않는다 — Cognito 자체가 이 scope를 지원하지 않으므로(아래 callout 참고), 켜는 옵션도 없다.
Cognito는 offline_access scope를 지원하지 않는다 — gateway.yaml에서도 빼야 한다. 게이트웨이는 refresh token을 받기 위해 기본적으로 openid profile email offline_access를 요청하는데, Cognito가 허용하는 scope는 openid·email·phone·profile·aws.cognito.signin.user.admin뿐이다. 위에서 Profile까지 체크했다면(App Client의 AllowedOAuthScopes), gateway.yaml의 oidc.scopes도 정확히 그 목록([openid, profile, email])으로 override해야 한다 — 안 하면 게이트웨이가 여전히 기본값(offline_access 포함)을 요청해 Cognito가 로그인 화면에 닿기도 전에 invalid_request: invalid_scope로 거부한다. 자세한 설정은 실습 가이드 단계 4에 있다. refresh token이 없어지는 대신, 게이트웨이의 session.ttl_hours를 늘려 재로그인 빈도를 줄인다.
Cognito는 공개 엔드포인트라 브라우저 도달 문제가 없다. 사설 IP resolution 제약은 게이트웨이 자신에만 적용되고 IdP에는 적용되지 않는다. Cognito 로그인 페이지는 공개 인터넷에서 열리므로, 랩탑 브라우저가 Cognito에 닿는 것은 문제가 아니다. 게이트웨이(사설 IP)에 닿는 경로만 Client VPN으로 마련하면 된다.

3 · 테스트 사용자 생성

개요 화면의 Users에서 테스트 사용자 1명을 만든다. 이때 email 검증 상태로 만들어야 한다 — email_verified: true가 아니면 게이트웨이가 로그인을 거부한다. 콘솔에서 사용자를 만든 뒤 속성에서 email_verified를 true로 표시하거나, 2단계의 이메일 자동 검증 흐름으로 검증을 마친다.

콘솔에서 만든 사용자는 FORCE_CHANGE_PASSWORD 상태로 시작한다. 콘솔의 Create user로 만들면 임시 비밀번호가 발급되고, 사용자 상태가 FORCE_CHANGE_PASSWORD로 남는다. 이 상태에서 Hosted UI로 로그인하면 새 비밀번호 설정 화면이 나와야 하는데, 정상적으로 처리되지 않으면 "Sign-in failed"로 실패한다. 테스트 목적이면 admin-set-user-password에 --permanent를 줘서 이 절차를 건너뛰고 바로 정식 비밀번호를 지정하는 게 확실하다. 
aws cognito-idp admin-set-user-password \
  --user-pool-id <pool-id> \
  --username <사용자의 sub 또는 username> \
  --password '<원하는 영구 비밀번호>' \
  --permanent \
  --region us-east-1
비밀번호는 User Pool의 비밀번호 정책(기본: 최소 8자, 대소문자·숫자·특수문자 포함)을 만족해야 한다. 실행 후 사용자 상태가 CONFIRMED로 바뀐다.

4 · 게이트웨이에 넘길 값 메모

gateway.yaml의 oidc 블록(실습 가이드 단계 4)에 넣을 값이다. 세 값을 메모해 둔다.

  • issuer — https://cognito-idp.us-east-1.amazonaws.com/<pool-id>
  • client_id — App Client의 ID
  • client_secret — App Client의 secret (환경변수 OIDC_CLIENT_SECRET로 주입)
막히면 여기부터.
  • 로그인은 됐는데 게이트웨이가 사용자를 거부 → 테스트 사용자의 email_verified가 true인지 확인한다.
  • 게이트웨이가 client secret 관련 오류 → App Client가 Traditional web application(secret 포함) 유형인지, OIDC_CLIENT_SECRET이 실제 secret과 일치하는지 확인한다.
  • 콜백 오류(redirect mismatch) → App Client의 콜백 URL이 https://<gateway-hostname>/oauth/callback과 정확히 일치하는지 확인한다.
  • invalid_request: invalid_scope → App Client의 OpenID Connect scopes(AllowedOAuthScopes)와 gateway.yaml의 oidc.scopes가 정확히 일치하는지, 특히 offline_access가 양쪽 모두에서 빠졌는지 확인한다.
  • Invalid request. Please check your input and try again. → App Client의 Identity providers에 Cognito user pool이 체크돼 있는지 확인한다.
  • "Sign-in failed" → 테스트 사용자가 FORCE_CHANGE_PASSWORD 상태로 남아 있는지 확인한다. admin-set-user-password --permanent로 영구 비밀번호를 지정한다.

출처: Create a new application in the Amazon Cognito console (공식 문서), Cognito user pool sign-in options (공식 문서)

이 문서의 설정을 실제로 적용하며 마주친 문제(scope 불일치, identity provider 누락, 임시 비밀번호 상태)는 트러블슈팅 로그에 순서대로 기록돼 있다.

Cognito 외 다른 OIDC IdP(Auth0·Okta·Entra ID 등)로 게이트웨이를 연결하는 방법이 필요하면 요청하세요.
